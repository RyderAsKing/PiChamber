# Pi extensions in PiChamber

PiChamber runs your existing [pi extensions](https://pi.dev/docs/latest/extensions/) inside every session. Extensions load from the same locations as the pi CLI — `~/.pi/agent/extensions/` (global) and `.pi/extensions/` (project-local, after project trust) — and keep their tools, commands, events, and session state.

On top of that compatibility layer, extensions can render rich UI directly inside PiChamber's chat with a small declarative protocol.

## What works out of the box

| Extension capability | Behavior in PiChamber |
| --- | --- |
| `pi.registerTool()` | Tools are callable by the model; results render as tool cards |
| `pi.registerCommand()` | Invokable from the composer as `/command args` |
| Lifecycle + agent events | Fully supported (`tool_call`, `before_agent_start`, compaction, …) |
| `ctx.ui.select / confirm / input / editor` | Rendered as a blocking dialog in the chat; the extension waits for your answer. A multi-line title shows its first line as a small label and the rest below it as written |
| `ctx.ui.notify` | Shown as a row in the chat where it arrived; live only, not saved to the session |
| `ctx.ui.setStatus(key, text)` | Shown above the composer until cleared |
| `ctx.ui.setWidget(key, lines)` | Lines shown above (or below) the composer |
| `pi.appendEntry()` / `pi.sendMessage()` | Visible in the chat transcript (see below) |
| `registerMessageRenderer()` (custom message renderers) | Rendered lines shown as the message body; expanded lines behind Show more, raw text under Raw message (see below) |
| `ctx.ui.custom()` | Drawn in the chat on a terminal screen in the colours of your Pi theme (Pi's default theme follows PiChamber's light or dark mode; a theme you set in Pi keeps its own colours): inline components take the composer's place, overlays float over the chat. Keys, clicks, drags and the mouse wheel go to the component (Shift+drag selects text). On a phone or tablet a tap is a click, a swipe scrolls, and a key bar adds Esc, Tab, the arrows, Enter and the on-screen keyboard; with a mouse, Show key buttons adds the same bar and Copy text copies what the component drew. `ctx.mode` is `"tui"`, so extensions that check for it run (see [Extension interface](#extension-interface)) |
| Other TUI-only surfaces (`setHeader`/`setFooter`, `onTerminalInput`, `setEditorComponent`, autocomplete providers, theme switching) | Intentional no-ops; use the GUI protocol instead |

Lines an extension draws with Pi's theme (`theme.fg("accent", ...)` and the like) take your Pi theme's colours wherever Pi would draw them: `custom()` components, tool renders, message renderers, widgets and statuses. Outside a `custom()` component they sit on PiChamber's background, so a Pi theme made for the other appearance (Pi's `dark` theme while PiChamber is light) falls back to PiChamber's colours there. Dialogs and notices use PiChamber's colours.

Extension errors don't abort your session — they surface as an error entry so you can see what failed.

## Turning extensions on and off

**Settings → Extensions & Plugins → Pi extensions** lists what Pi loads, the
same list `pi config` shows in a terminal. It reads and writes Pi's own
settings files, so a change made here applies in the pi CLI too, and a change
made in the CLI shows up here.

- **Global** has a switch per extension. Off means Pi stops loading it in
  every project.
- **This project** appears when a folder is open. Each extension has a
  switch for that project only. An extension you switch away from its global
  setting says "On in this project only" or "Off in this project only".
  Switch it back and the project follows the global setting again. Pi must
  trust the project first; until then the page shows the global list without
  controls.
- **Packages** installed with `pi install` or from Browse are listed with
  their version and extensions. An npm package shows **Update to X** when npm
  has a newer version; a package pinned to a version (`npm:name@1.2.3`) is
  left as it is. Remove deletes a package the way `pi remove` does: an npm or git package's
  files are deleted, a local folder is only dropped from settings and stays
  on disk. A global package is removed from Global, a project's package from
  This project.
- **Built into Pi** lists the extensions that ship with Pi (`mcp`,
  `codemode`, `tool-search`). Pi's llama.cpp provider is not offered because
  PiChamber does not load it.

Running sessions pick a change up when they are idle. The page changes Pi on
the machine that runs the PiChamber server, also when you open it from a
phone or another computer. Skills, prompt templates, and themes from packages
keep their own pages.

## Finding and installing packages

**Browse**, at the top of Settings → Extensions & Plugins, searches the Pi
packages on npm: every npm package with the `pi-package` keyword, the same
list as Pi's package gallery. PiChamber hosts no registry of its own. The
PiChamber server asks npm and reads only each package's metadata (name,
description, version, maintainer, license, downloads, links), never its
README or images.

- **Featured** is a short list kept in the PiChamber repository. The server
  checks it for changes every few hours and falls back to the copy it
  shipped with.
- **Enhanced for PiChamber** shows packages that add features only
  PiChamber shows, built with the PiChamber plugin SDK, as their authors
  mark them. Every Pi package works in PiChamber; these do more here. A package's page checks that its
  `package.json` really says so.
- PiChamber's own plugins never show as results. When a search matches one,
  it shows first with its switch, since it is already installed.

**Install** asks where to load the package: every project (`pi install`) or
only the open project (`pi install -l`), which Pi must trust first. A package
runs as code with Pi's access on the server's machine, so install only
packages you trust. The install runs in the background; the package shows
under Packages when it is done.

## Marking a package as enhanced for PiChamber

Add the `pichamber-plugin` keyword next to `pi-package` in `package.json`,
and declare a `pichamber` block with the API version you target:

```json
{
  "keywords": ["pi-package", "pichamber-plugin"],
  "pichamber": { "apiVersion": 1 }
}
```

The keyword puts the package under Enhanced for PiChamber in Browse; the block
is what its page checks. Installed packages with the block get an Enhanced tag
with the PiChamber mark under Packages. They load as plain Pi packages, here and in the terminal.

### When your extension replaces a plugin

Pi loads only one extension for each tool, command, or flag name. PiChamber's
plugins and Pi's built-ins step aside for your own extension, so a plugin can
be switched on and still not be loaded. For example, your own `subagent`
extension takes the place of the Sub-agents plugin.

When a session is running in the folder, the page shows it. The plugin's row
says "Not loaded" and names the extension, and the plugin's own page has a
button that turns that extension off. The extension's row says what it was
loaded in place of. With no session running there is nothing to compare, so
no notice shows.

## Extension interface

**Settings → Sessions → Extension interface** chooses what extensions are told
about the interface. It applies to sessions started after you change it.

- **Terminal UI** (default): `ctx.mode` is `"tui"`. Extensions that check for a
  terminal draw their own components with `ctx.ui.custom()`, as in the pi CLI,
  and you answer with the keys they show.
- **Standard dialogs**: `ctx.mode` is `"rpc"`, pi's mode for frontends.
  Each extension decides what to do without a terminal. Some ask with
  `ctx.ui.select` or `confirm`, which PiChamber shows as clickable dialogs.
  Some show less or skip their screen, and some may pick a default answer
  without asking. Extensions that call `ctx.ui.custom()` without checking the
  mode still draw their terminal UI.

## Compatibility principle

PiChamber adapts itself to pi extensions rather than the other way around. An
extension that knows nothing about PiChamber keeps working: its tools, commands,
hooks (`tool_call`, `before_agent_start`, `context`, `before_provider_request`,
compaction, `session_*`, `agent_*`, `turn_*`, `message_*`, `tool_execution_*`,
`input`, `user_bash`, etc.), prompt modifications, and `ctx.ui` dialogs all run
inside the daemon's pi runtime via the SDK's canonical discovery and trust flow
(`~/.pi/agent/extensions`, `.pi/extensions`, package `pi.extensions`). PiChamber
only adds an optional enhancement when the extension opts in.

## Detecting PiChamber (optional)

Do not make PiChamber a hard dependency. Check at runtime. `ctx.mode` does
not tell PiChamber apart: it is `"tui"`, as in the pi CLI, or `"rpc"` when the
user chose standard dialogs.

```ts
const isPiChamber = (): boolean => {
  const marker = (globalThis as Record<string, unknown>).__PICHAMBER__ as { version?: number } | undefined;
  if (marker?.version) return true;
  try { return typeof process !== 'undefined' && process.env.PICHAMBER === '1'; } catch { return false; }
};

pi.on('session_start', async (_event, ctx) => {
  if (isPiChamber()) ctx.ui.setStatus('my-ext', 'PiChamber mode');
});
```

Keep the check local to your extension. It has no PiChamber runtime dependency,
so the same extension continues to work in the plain pi CLI.

PiChamber's own calls live on `globalThis.pichamber`, a frozen object with
`version` and `ui`. They are not on pi's `ctx.ui`: if pi later adds a method
with the same name and another shape, ours would shadow it. Each call takes the
tool or handler `ctx` first, which tells PiChamber the session.

```ts
const pichamber = (globalThis as any).pichamber;
if (pichamber) await pichamber.ui.openUrl(ctx, "http://localhost:3000");
```

Without `ctx`, or with a `ctx` from outside a PiChamber session, a call rejects
with a `TypeError`.

## Composer controls

An extension can put a switch, a mode picker, or a button in the composer
footer, beside the model and thinking controls. It emits `pichamber:composer`
on Pi's shared event bus. The pi CLI has no listener, so the event does
nothing there and the extension's commands keep working as before.

Each control names the extension's own slash commands. A click in PiChamber
runs one of them as if you had typed it, and the extension reports its new
value by emitting again. The extension owns the value: PiChamber only shows
what was last reported.

```ts
// Economy → Balance → Premium, one click each.
const publishMode = (active: string | undefined) => {
  pi.events.emit('pichamber:composer', {
    id: 'mode',
    kind: 'cycle',
    label: 'Mode',
    description: 'Model and thinking presets',
    value: active,
    options: [
      { value: 'economy', label: 'Economy', command: 'economy' },
      { value: 'balance', label: 'Balance', command: 'balance' },
      { value: 'premium', label: 'Premium', command: 'premium' },
    ],
  });
};
// Call it at session_start and whenever the mode changes, including from
// model_select and thinking_level_select when the model changes some other way.

// A toggle: `command` flips it, `value` says whether it is on.
pi.events.emit('pichamber:composer', { id: 'plan', kind: 'toggle', label: 'Plan', value: planOn, command: 'plan' });

// A button that runs a command.
pi.events.emit('pichamber:composer', { id: 'review', kind: 'action', label: 'Review', command: 'review --staged' });

// Take a control away.
pi.events.emit('pichamber:composer', { id: 'plan', remove: true });
```

- `id`: lowercase letters, digits and dashes, up to 40 characters. Emitting
  the same id again replaces the control.
- `kind`: `toggle`, `cycle` (2 to 12 `options`), or `action`.
- `command`: one of your registered commands, with or without the `/`, and
  optional arguments. Unregistered commands are refused when clicked.
- `label` (up to 40 characters) and `description` (up to 200) are optional
  text for the pill, its tooltip, and the phone sheet. `icon` is drawn only
  when PiChamber knows the name.
- A session shows its first 16 controls. Controls clear when the session
  reloads, so emit them again at `session_start`.

On desktop each control is a pill: a toggle lights up while on, a cycle
shows its current option and moves to the next on click, an action runs its
command. On phones they are rows in the composer controls sheet, where a
cycle shows every option to pick from. A click while the agent works runs
the command at once, as a typed command would. Clicks never add anything to
the transcript or the session title.

A new session has its controls before you send anything. When you open one,
PiChamber starts a session for it in the background, so your extensions load
and declare their controls as usual. Until that is ready, the composer shows
the controls the folder had last time. A click made before then waits and
runs once the session is ready. Your first message goes to that same
session, so a mode you picked is still picked. If you close the draft or
pick another folder, the background session ends. Nothing is written to disk
until you send, and the session list never shows it. Your extension sees an
ordinary `session_start`, so it needs no changes.

## The PiChamber GUI protocol

Any extension can emit a UI card by appending a custom entry or sending a custom message whose type is `pichamber.ui`:

```ts
import type { ExtensionAPI } from "@earendil-works/pi-coding-agent";

export default function (pi: ExtensionAPI) {
  pi.registerCommand("explore-status", {
    description: "Show explore progress",
    handler: async () => {
      // Chat transcript card with a live progress bar and action button
      pi.appendEntry("pichamber.ui", {
        title: "Explore",
        component: "progress",
        props: { label: "Files indexed", value: 40, max: 200 },
        actions: [
          { label: "Focus src", command: "explore-focus", args: "src" },
        ],
      });
    },
  });
}
```

The payload is plain JSON — no markup, no scripts — so it is safe to render on
web, desktop, and mobile. Include the versioned protocol marker so future
breaking changes do not crash older clients:

```ts
pi.appendEntry('pichamber.ui', {
  protocol: 'pichamber-extension-ui',
  version: 1,
  title: 'Sub-agents',
  component: 'table',
  props: { columns: ['Agent','Status'], rows: [['research','running']] },
  actions: [{ label: 'Cancel', command: 'subagents-cancel', args: 'research' }],
});
```

- `protocol` / `version`: `pichamber-extension-ui` / `1`. Unknown versions
  degrade to a generic JSON fallback instead of breaking the chat.
- `id`: optional stable identity (≤128 chars), reserved for live panels.
  PiChamber does not render live panels yet, and an entry with an `id` is kept
  out of the transcript. Leave `id` off if the card should show in the chat.
- `component`: one of `markdown`, `kv`, `list`, `table`, `progress`, `badges`, `code`
- `props`: component properties (validated; unknown components degrade to a generic card)
- `actions`: up to 8 buttons. Each invokes a registered extension command through the normal prompt path, so the handler receives the arguments and can drive the agent
- `title`: optional card heading (≤256 chars)

### Component reference

```ts
// markdown
{ component: "markdown", props: { body: "**Indexed** 12 files" } }

// key-value rows
{ component: "kv", props: { rows: [{ label: "Files", value: "12", tone: "info" }] } }

// list
{ component: "list", props: { items: [{ label: "src/", value: "42 files" }] } }

// table
{ component: "table", props: { columns: ["File", "Status"], rows: [["a.ts", "done"]] } }

// progress bar (value/max)
{ component: "progress", props: { label: "Indexing", value: 40, max: 100 } }

// badges
{ component: "badges", props: { items: [{ label: "passing", tone: "success" }, "3 skipped"] } }

// code block
{ component: "code", props: { language: "ts", code: "const x = 1;" } }
```

Tones: `info`, `success`, `warning`, `error`, `neutral`.

### Actions invoke your commands

Action buttons send `/<command> <args>` through PiChamber's prompt path. Register matching commands with `pi.registerCommand()`:

```ts
pi.registerCommand("explore-focus", {
  description: "Focus exploration on a directory",
  handler: async (args, ctx) => {
    ctx.ui.notify(`Exploring ${args || "."}`, "info");
  },
});
```

Actions support optional fields beyond `label`/`command`/`args`/`variant`:

- `icon`: PiChamber sprite icon name rendered before the label (unknown names are ignored)
- `disabled`: render disabled and ignore clicks
- `loading`: show a spinner while still clickable-disabled until the next card arrives
- `confirm`: ask the user to confirm before invoking (destructive actions)
- `promptForArgs`: `{ label?, placeholder? }` — collect an argument string through an inline input before invoking

### Live panels are not rendered yet

PiChamber does not render live panels. The daemon still mirrors a
`pi.appendEntry()` entry that carries a stable `id` into `extension.ui` events
and per-session panel state. The latest descriptor for each `id` replaces the
previous one, and `{ id, removed: true }` unregisters it. No client reads that
state, and the daemon keeps those entries out of the transcript, so a
`pichamber.ui` entry with an `id` is not visible anywhere. Leave `id` off to
get a transcript card. A `pichamber.ui` custom message published with
`pi.sendMessage()` is always a transcript card and participates in model
context.

### Editor dialogs

`ctx.ui.editor(title, prefill)` opens a multiline blocking dialog. Submit
returns the current text, including an empty string. Cancel returns
`undefined`.

### Structured form dialogs

`pichamber.ui.form(ctx, title, fields)` asks for several typed inputs at once
(plain pi has no such call, so check that `pichamber` exists first):

```ts
const pichamber = (globalThis as any).pichamber;
if (pichamber) {
  const values = await pichamber.ui.form(ctx, "Spawn agent", [
    { id: "name", label: "Name", type: "text", required: true },
    { id: "task", label: "Task", type: "textarea" },
    { id: "priority", label: "Priority", type: "select", options: ["low", "high"], initial: "normal" },
    { id: "dryRun", label: "Dry run", type: "checkbox", initial: "true" },
  ]);
  // values: Record<fieldId, string>, or undefined when cancelled or timed out.
}
```

Releases up to 1.0.7 had these two calls as `ctx.ui.form(title, fields)` and
`ctx.ui.openUrl(url)`. Both are removed. Call `pichamber.ui.form(ctx, title,
fields)` and `pichamber.ui.openUrl(ctx, url)` instead.

Field types: `text`, `textarea`, `number`, `select`, `checkbox`. The dialog is
blocking like `ctx.ui.input` and resolves with a values object keyed by field
id. The daemon validates required fields, number bounds, select options, and
checkbox values before resolving the extension. Fields are capped at 12;
options at 20.

### Choice dialogs

`pichamber.ui.choose(ctx, title, choices, options)` asks the user to pick one of
a few choices, each with a short description, and can take a note with the
answer (plain pi has no such call, so check that `pichamber` exists and fall
back to `select`):

```ts
const pichamber = (globalThis as any).pichamber;
if (pichamber) {
  const answer = await pichamber.ui.choose(ctx, "Which layout?", [
    { id: "grid", label: "Grid", description: "Cards in three columns" },
    { id: "list", label: "List", description: "One row per item" },
  ], { allowNote: true });
  // answer: { id: "grid", note?: "..." }, or undefined when closed or timed out.
}
```

Up to 12 choices. `options` takes `message` (a line under the title),
`allowNote`, and the `signal` and `timeout` every dialog takes. The daemon
only accepts an answer whose id is one of the choices. PiChamber's bundled
plugins also pass `toolCallId` from a tool's `execute`, which lets their own
chat components show the question beside what it is about; for other
extensions the question appears above the composer like any dialog.

The bundled Visuals plugin builds on this: its `render_choices` tool shows a
few page or image variants in the chat, one at a time at full width with
buttons to switch between them, and returns the one you picked, with your
note.

### Sandboxed app surfaces

PiChamber does not render app surfaces yet. The daemon accepts and stores
`pichamber.app` entries as described here, but no client displays them.

For richer custom UI, an extension can register an app surface by appending a
`pichamber.app` entry containing self-contained HTML. It is designed to render
inside an iframe sandboxed with script execution only — no same-origin access to
PiChamber, no cookies or storage, no navigation. The only capability granted
back is firing registered slash commands from elements carrying
`data-pichamber-command` / `data-pichamber-args`:

```ts
pi.appendEntry("pichamber.app", {
  protocol: "pichamber-extension-ui",
  version: 1,
  appId: "board",
  title: "Kanban board",
  html: `<button data-pichamber-command="board-next">Next</button>`,
});
// Remove it again with: { appId: "board", removed: true }
```

The command name must match `[A-Za-z0-9][A-Za-z0-9:_-]{0,127}` — no path
separators — and runs through the same authenticated prompt path as action
buttons. HTML is capped at ~200 KB per app and 8 apps per session.
### State ownership and transport

Declarative cards are `appendEntry` / `sendMessage` entries in the pi JSONL.
They survive reloads and are served to late-joining devices via the same
`GET /api/pi/sessions/:id` hydration that restores the transcript. Incremental
`appendEntry` updates create new transcript rows. An appended entry with a
stable `id` goes to live panel state instead of the transcript. Custom messages
remain transcript-only.

Live ephemeral state (`ctx.ui.setStatus`, `ctx.ui.setWidget`, pending
`ctx.ui.select/confirm/input/editor/form` dialogs, live `pichamber.ui` panels,
and registered `pichamber.app` surfaces) is kept as server-side
normalized state per `sessionId`. The daemon mirrors it into the `session.snapshot`
so a reconnect that missed the 1k retained `extension.*` event window still
rebuilds the current sub-agent list or approval prompt.

All extension UI travels through the normal authenticated event stream
(`/api/pi/events` via `runtimeFetch` / relay tunnel). No second WebSocket or
custom origin is required; browser, Electron, and Capacitor clients share the
same transport.

### Custom message renderers

When an extension registers a message renderer (for example a
`subagent-notification` renderer), the daemon renders the custom message at
100 columns and attaches the ANSI lines to the message. PiChamber shows those
lines as the message body. Longer output hides behind a Show more toggle that
swaps to the expanded lines, and the original text plus details stay
available under a collapsed-by-default Raw message disclosure. Messages
without a renderer keep the existing note display.

### Anything else falls back gracefully

Custom entries or messages that don't carry a `pichamber.ui` descriptor still appear in the chat as a collapsed card showing their content — internal state entries stay visible but never break rendering. Future major `version` values also fall back rather than crashing.

## Sub-agent reference pattern

```ts
import type { ExtensionAPI } from '@earendil-works/pi-coding-agent';

export default function (pi: ExtensionAPI) {
  const agents = new Map<string, { name: string; status: string; task: string }>();
  const render = () => pi.appendEntry('pichamber.ui', {
    protocol: 'pichamber-extension-ui',
    version: 1,
    title: 'Sub-agents',
    component: 'table',
    props: { columns: ['Agent','Status','Task'], rows: [...agents.values()].map((agent) => [agent.name, agent.status, agent.task]) },
    actions: [{ label: 'Clear', command: 'subagents-clear' }],
  });

  pi.registerTool({
    name: 'spawn_subagent',
    description: 'Spawn a tracked sub-agent',
    parameters: { type: 'object', properties: { name: { type: 'string' }, task: { type: 'string' } } } as never,
    async execute(_id, params) {
      agents.set(params.name, { name: params.name, status: 'running', task: params.task });
      render();
      return { content: [{ type: 'text', text: `Spawned ${params.name}` }], details: {} };
    },
  });

  pi.registerCommand('subagents-clear', {
    description: 'Clear finished sub-agents',
    handler: async (_args, ctx) => { agents.clear(); render(); ctx.ui.notify('Cleared', 'info'); },
  });
}
```

Each `render()` call appends a new card to the transcript.

A full working demo is `packages/web/server/lib/pi/fixtures/pichamber-gui-demo.ts`.

## Notes for project-local extensions

Project-local extensions participate in pi's standard trust flow. When PiChamber opens a project that hasn't been trusted yet, pi resolves trust exactly as it does on the CLI.

## Security and limits

- Declarative payloads are validated and truncated (keys ≤128, titles ≤256,
  badge items ≤24, table rows ≤200, messages ≤50k). Unknown `pichamber.ui`
  components never execute code.
- Actions map to registered slash commands and are invoked through the
  authenticated prompt path — never arbitrary function calls.
- Extension UI state is scoped per `sessionId` and never leaks across sessions
  or directory scopes.
- Raw HTML in extension messages is rendered as inert text and sanitized.
- App-surface HTML runs in a script-only sandboxed iframe: no same-origin
  access, no storage or cookies, no navigation, and its single capability
  (invoking slash commands) is bound to a per-mount random token validated by
  the host before any prompt is sent.
- `GET /api/pi/extensions` returns opaque extension ids only — server
  filesystem paths never cross the API boundary.

## User-authored command triggers

Users can pin any registered slash command as a quick-action button near the
composer and optionally bind a global keybinding to it (Settings → Shortcuts →
Command triggers). Triggers are stored in shared ui-settings, fire the same
authenticated prompt path, and always match after built-in shortcuts so they
can never shadow core actions. This restores CLI-style muscle memory (for
example cycling model modes without touching the mouse) for extensions that
register commands instead of terminal keyboard hooks — `pi.registerShortcut()`
remains TUI-only and does not fire in PiChamber sessions.
