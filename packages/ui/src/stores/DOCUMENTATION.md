# UI Stores

`packages/ui/src/stores` owns shared Zustand state for PiChamber UI preferences and Pi-native resource views.

Use a store only for state shared across distant component trees or for a cache whose ownership is explicit. Keep high-frequency session events in the Pi session store rather than broad UI stores, and use narrow selectors so unrelated UI does not rerender.

## Ownership

- `useUIStore.ts`: local UI layout, dialogs, and presentation preferences. `ui/contextPanel.ts` owns context-panel tabs, deduplication, width clamping, and directory-scoped persistence sanitization. `ui/githubSelection.ts` owns the persisted per-directory `host/owner/repo` pick (`githubSelectedRepoByDirectory`, sanitized + root-clamped like `contextPanelByDirectory`, survives reload).
- `useGitHubStatusStore.ts`: gh status per runtime (installed/version/hosts with login/scopes), in-flight dedupe by runtime, throttled refresh on window focus/visibility. Reset on runtime switch; failure preserves last-known status.
- `useGitHubScopeStore.ts`: scope + selection per directory (repositories in scope, default selection, truncated flag, errors). Entries keyed by runtime + directory with in-flight coalescing and generation guards; failed refresh keeps previous scope marked stale. Selection resolves persisted pick → scope default → containing → first selectable, persisted via `useUIStore.setGitHubSelectedRepo` (allow-list validated). `invalidate` calls `POST /api/github/invalidate` then re-reads.
- `github/githubAsyncResource.ts`: generic keyed async-resource helper for list/detail entries — last-known-first, background revalidation, generation stale guards, failed refresh keeps data marked stale with error (never empty), in-flight coalescing, explicit invalidate, runtime in keys, `reset()` on runtime switch. An optional `onSettle` hook fires after every settled load, including the background revalidation `ensure` starts for cached entries. Per-key `subscribe(key, listener)` plus `useKeyedResourceEntry(resource, key)` re-render only that key's subscribers, so a load settling for one PR never notifies another PR or repo list. `markStale` flags an entry for revalidation without fetching; `setError` records a page-level failure while keeping loaded items. Entries are LRU-bounded (`maxEntries`, default 200): least-recently-used non-inflight, unsubscribed entries evict on a deferred pass, never on the acquisition path.
- `github/githubListCore.ts`: shared list/detail/comments machinery for the pull-request and issue stores, parameterized by key builders, query builders, and loaders. Owns the four keyed resources, the remote-search repo index, single-flight page guards, per-repo remote-query cap (last 10), filters/selection slices, and every shared operation (collections, remote search, detail/comments, `refreshAllForScope`, `markCollectionsStale`). Load-more failures record the error inline via `setError` while keeping loaded items and their cursor. Thin per-entity stores keep only PR-only (files, checks, actions, reviews/threads) and issue-only bits.
- `useGitHubIssuesStore.ts`: issue lists and details on the shared list core (lists are two wide collections keyed runtime + repo + `open`/`closed`, cursor pages merged; detail + comments keyed runtime + repo + number; detail carries linked pull requests, viewer permission/capabilities, and section errors through). State/involvement/labels/search/sort are local views (`githubListFiltering`) — collection keys never include them. Stale-while-revalidate with a 30 s fresh window plus closed prefetch; failed refreshes keep data marked stale, never empty. Per-query remote search entries (`state + involvement + labels + q`, perPage 50, last 10 per repo) merge hits into the repo index for reselect; one failed fetch never wipes loaded data. Components subscribe per key (`useIssuesCollectionEntry`, `useIssuesRemoteEntry`, `useIssueDetailEntry`, `useIssueCommentsEntry`); selection uses `selectIssue`. Comments post optimistically (negative-temp-id insert) and reconcile against the authoritative re-read, with rollback on failure. Optimistic updates only for the viewer's own actions (state incl. close reason, labels, assignees, title/body) with rollback; post-action server invalidate then re-read both collections and drop the repo's remote caches; no list polling. Agent-turn completion also marks the repo's collections stale so the next visible list revalidates once.
- `useGitHubPrStatusStore.ts`: current-branch PR status for Git chips and sidebar badges. Entries keyed by runtime + directory + branch; polling tiers from plan §7.2 (open + pending 1 min; open + settled 5 min; no PR 5 min; paused while hidden, resumed on visible with sequential revalidation, max 1 in flight). Bounded to 100 branch entries (least-recently-accessed evict first). `usePrVisualSummary` derives number + checks state; `useEnsureGitHubPrStatus` loads via the registered runtime API. `selectPrChecksIndex` derives the per-URL checks index once per `results` change for row consumers.
- `useGitHubPullRequestsStore.ts`: PR list/detail/comments on the shared list core plus PR-only files/checks resources — lists are two wide collections keyed `runtime + repo + open/closed` (`closed` holds merged + closed, split locally; cursor pages merged), detail/comments/files/checks keyed `runtime + repo + number`. State/involvement/search/sort are local views (`githubListFiltering`) — collection keys never include them. Stale-while-revalidate with a 30 s fresh window plus closed prefetch; failed refreshes keep data stale, never empty. Per-query remote search entries (`state + involvement + q`, perPage 50, last 10 per repo, in-flight coalesced per key) merge hits into the repo index for reselect; one failed fetch never wipes loaded data. Components subscribe per key (`usePullsCollectionEntry`, `usePullsRemoteEntry`, `usePullDetailEntry`, `usePullCommentsEntry`, `usePullFilesEntry`, `usePullChecksEntry`) with action/leaf zustand selectors — never the whole store. Load-more failures (collections, remote, comments, files) record the error inline while keeping loaded items and their cursor; file paging shares the single-flight guard. Optimistic updates only for the viewer's own actions (title/body, state actions, conversation comments with a negative-temp-id insert) with rollback; post-action server `invalidate` then re-read both collections and drop the repo's remote caches (comments reconcile against the authoritative re-read); no fixed list polling (surface open / focus / repo change / explicit refresh). Owns list filters + PR selection handoff (`selectPullRequest`/`openPullRequestInSurface`) and per-repo merge-method memory (`readMergeMethod`/`setMergeMethod`; no store mirror). Review submits take an explicit `{ event, body, comments }` snapshot — pending-review state lives in `github/useGitHubPendingReviewStore`, never here. `notifyAgentTurnComplete`/`subscribeToAgentTurnCompletion` invalidate pr-status + open detail from the sync layer's turn-complete notifications (`useNotificationStore`, fed only by live `PiSessionStore` lifecycle events), marking the repo's collections stale so the next visible list revalidates once.
- `github/useGitHubPendingReviewStore.ts`: in-memory pending-review state keyed `${repo}#${number}` — line comments awaiting submit, review summary + verdict, and the standalone comment draft (all survive composer mode switches and popover close). The comment draft slot also holds unposted issue comments (issue and PR numbers share one sequence per repo, so `${repo}#${number}` never collides), keeping the PR and issue comment forms consistent. Deliberately never persisted: a half-written review is invisible until one submit request carries summary + verdict + every line comment together, so there is no server draft to reconcile. Submit clears only what was sent (submitted comment ids; summary only when still equal to the submitted text; remarks added mid-flight stay). Selectors return frozen stable fallbacks, never fresh arrays. Reset on runtime switch.
- `useDirectoryStore.ts`, `useProjectsStore.ts`, `useGitStore.ts`, `useWorktreeStore.ts`, `useWorktreeCreationStore.ts`, `useTerminalStore.ts`, `useFilesStore.ts`: workspace chrome for Files/Git/Terminal against `/api/fs`, `/api/git`, `/api/terminal`. `useWorktreeStore` owns runtime-scoped authoritative Git worktree topology per registered project; refresh failure preserves the previous list and remains distinct from successful empty discovery. `useWorktreeCreationStore` owns in-memory, runtime-scoped worktree task progress so naming/create/bootstrap polling survives composer unmounts. Each submitted draft supplies a unique task ID, allowing separate drafts with the same source and start ref to run concurrently while duplicate requests for one task share an in-flight promise. Completed receipts stay available to the Background tasks menu, their success notification is claimed once, stale generations never overwrite a newer entry, re-entering naming/in-flight structurally clears a prior `failedSend`, and a successful `setup-ready` worktree still records a receipt if project refresh fails. A failed creation retains its prompt, confirmed mentions, and immutable attachment snapshot in task-owned `failedSend` memory (never `localStorage`) until an explicit Restore draft action or dismiss; the receipt retains that snapshot while session materialization/prompt dispatch is pending, prompt acceptance consumes the exact generation via `markWorktreePromptSucceeded` so Background tasks does not linger with a misleading Open action, and post-receipt prompt failure transitions the same entry to failed via `markWorktreePromptFailed` with the snapshot intact and Restore draft available (both guarded to the exact `failedSend` identity, so a late success/failure never clears or overwrites a newer generation); the menu stays thin and recovery lives in `composer/submit/worktreeFailedSend.ts`, which reopens the original source directory and worktree intent under a runtime guard, restores mentions with the prompt, appends missing attachment ids transactionally against the 20-attachment limit so newer files survive and overflow keeps the record with actionable copy (expired ids refresh from the retained data URL), refuses occupied targets, consumes the record once on success only for the same failed payload it read (`consumeFailedSend` ownership guard, so a newer in-flight/completed/re-failed generation is never cleared), and releases it on dismiss or runtime reset. Automatic PiChamber-era project-icon discovery is an intentional unsupported no-op until Pi-native icon storage has an owning contract.
- `useSkillsStore.ts`: Pi resource-discovery state. Skill paths are opaque daemon identifiers, never filesystem paths.
- `useSnippetsStore.ts`: PiChamber-owned `#name` literal-expansion snippets backed by `/api/pi/snippets` and `snippets-store.js` (`snippets.json` in the PiChamber data root). Snippets never read or write Pi prompt-template files and never process `$1`/`$@`. Mutations use opaque IDs, enforce case-insensitive name/alias uniqueness per effective bucket, and support rename plus global/project scope moves through a single serialized atomic read-modify-write; a failed move or rename leaves the original intact. Authoritative snapshots are keyed by runtime and effective directory; directory switches never reuse another directory's rows, fetch failure preserves that directory's last known snapshot and stays distinct from authoritative empty and malformed outcomes, project names override matching global names during `#` expansion, aliases expand literally, and runtime switches clear every snippet cache. PiChamber snippets require no Pi project trust.
- `usePromptTemplatesStore.ts`: Pi-owned `/name` prompt-template state projected from Pi resource discovery (`/api/pi/resources`, `/api/pi/commands`). Templates are edited only through daemon-owned `resources.prompts.create/update/delete` with an explicit effective directory and opaque resource IDs; package/path prompts stay visible but read-only. Project mutations require Pi project trust, busy runtime activation is deferred until a safe lifecycle edge, and the UI distinguishes that result from a failed write. Unknown frontmatter fields survive edits, rename validates the destination, rejects collisions, writes the destination atomically, removes the source only after success, and rolls back the destination when source removal fails. The daemon refreshes Pi resources and clears its service cache after success so `/commands` autocomplete reflects the change on its next fetch; failed fetches preserve the prior same-directory snapshot and stale runtime or cross-directory completions never commit. Web, Electron, hosted-mobile, and Capacitor all use the connected server's storage through `runtimeFetch`/`piClient`. New-session starter chips are pinned prompt templates from this catalog plus one-time built-in text defaults (`explore`/`plan`/`review`/`find-bugs`/`write-tests`, never skills, snippets, or extension commands): global starters persist in PiChamber global settings, project starters in project config, resolved against the effective new-session directory with project override winning for same-named prompts and identical `/name` invocations never shown twice. Fresh installs (`globalDraftStarters === null`) show the five built-in text chips; removing one persists the remainder so dismissed defaults never reappear and the `+` picker never offers them back. Prompt clicks insert `/name ` for editing (focus + caret after the trailing space, attachments/draft preserved, no session until send, no PiChamber expansion); text clicks insert literal prompt text; legacy skill/command starters are parsed defensively but dropped without conversion on sanitize/persist, idempotently. Deletion hides unresolved prompt starters only after an authoritative catalog; failures preserve; rename with old/new names updates pins deterministically, otherwise the old ref is removed rather than guessed.
- `useConfigStore.ts` orchestrates project-scoped provider state and publishes model/thinking picker selections. `config/defaults.ts` owns runtime/sidecar default precedence, `config/selection.ts` owns provider/model/thinking selection policy, `config/directoryScope.ts` owns project/worktree config routing plus its runtime-scoped persisted worktree mapping, and `config/modelMetadata.ts` owns models.dev validation, fetch deduplication, idle-deferred scheduling, and live-provider metadata fallback. The models.dev download (~424 KB) starts via `scheduleModelMetadataLoad` after first paint (`requestIdleCallback`, fallback `setTimeout 1500` for Safari/WKWebView which lacks it) from `initializeApp`, never inside `loadProviders`; any earlier `getModelMetadata`/`ensureModelMetadata` read starts it immediately (deduped, single in-flight). Failures never masquerade as authoritative empty metadata and remain retryable after a 30 s cooldown, so render-driven reads cannot restart the download on every render (`invalidateModelMetadataCache` clears the cooldown). The generic agent registry/loading/selection layer was removed: the Pi daemon exposes no agent list endpoint, so `agents`/`currentAgentName`/`applyDefaultModelAgentSelection` no longer exist and old persisted snapshots are sanitized on hydrate (obsolete `agents`/`currentAgentName`/`agentModelSelections`/`runtimeDefault*` keys are dropped, never re-persisted). Per-session agent/model/variant preferences live canonically in `sync/selection-store.ts` (the legacy `stores/contextStore.ts` was retired; its persisted variants and `currentAgentContext` fallback were migrated once into the canonical store, which now persists variants itself).
- `useUpdateStore.ts` owns client update checks for every runtime. In Electron it keeps the desktop client result in `info`; when the client uses a remote instance, it also checks that connected server against its own version and keeps the result in `serverInfo`. The local Electron instance remains a single desktop update target.
- `messageQueueStore.ts`: persisted per-target follow-up queues (persisted v2, no migration for the newer optional markers; legacy v1 session-only queues stay quarantined). Each entry carries queue-time send config plus optional durable delivery state: `deliveryAttempt` (`kind` + stable queue id as `operationId` + current `streamEpoch`, set synchronously before delivery so reload holds) and `sendFailed` (fixed boolean label for confirmed rejections, never raw error text). Transient `sendingIds` claims drive the Sending indicator and the edit/remove/send guard. `claimQueuedMessage` reads the latest store and refuses sending or attempted ids, plus targets without a current matching epoch (Check status first — receipt key includes kind) while allowing failed ids for explicit Steer; `getAutoSendCandidate` skips failed entries but holds FIFO behind earlier sending/attempted entries; `completeQueuedSend` is the only remover allowed while claimed; `removeFromQueue`/`popToInput` refuse claimed ids on the latest store. `queuedSendReceipt.ts` owns the full-key read-only receipt query (removes only on `accepted`) and `PiSendUnconfirmedError` detection; manual status checks never send. `requeueWithNewIntent` is the only store action that replaces a held operation id, and automatic send paths never call it.

`useSessionFoldersStore.ts` keeps a runtime-scoped browser snapshot for immediate continuity and reconciles it with the active server's validated `/api/pi/session-folders` sidecar. Missing server state is not authoritative empty state, and in-flight hydration cannot replace newer local mutations.

`config/defaults.ts` reads runtime defaults from the shared settings document already fetched by `lib/persistence.ts` (`loadSharedSettingsDocument`, the same runtime-scoped cached `/api/pi/ui-settings` GET) instead of issuing its own request; a failed or other-runtime document returns `null` and falls back to the dedicated defaults paths, so a fetch failure is never treated as empty defaults.

Model-picker and appearance preferences hydrate from the active runtime before autosave starts. Every later change is eligible for persistence. Both subscriptions stop during app teardown or a runtime switch so the next runtime captures a fresh baseline, while pending writes drain against their captured runtime. When upgrading a local runtime whose older shared settings omit session-pruning fields, hydration migrates the existing local pruning values before authoritative defaults can replace them. This migration never copies those values into a remote runtime.

Shared settings have no server push. After boot, `lib/settingsResumeSync.ts` calls `refreshDesktopSettings()` (`lib/persistence.ts`) when the page becomes visible or focused, when the network returns, and when the mobile shell recovers its connection, so a change made by another client of the same server (sidebar view, folder list and order, appearance) arrives through the same GET, sanitizers, and store-apply path as boot. A refresh is floored at 5 s, does not start while a local write is pending or in flight, drops its result when a local write was made during the GET, and changes nothing when the GET fails. A GET that overlaps an adopted PUT response never replaces the cache or the no-op suppression image. A write is never suppressed as a no-op for a key that an unsettled PUT carries, so restoring a value while its change is still in flight reaches the server. A refresh never adopts `activeProjectId`: which folder is open is per-client navigation state after boot.

`useProjectsStore.synchronizeFromSettings()` treats the settings document as the owner of folder order: `manualProjectOrder` is replaced with the incoming `projects` array order, so a reorder made on another client is not overridden by a stale local order. A document without `activeProjectId` keeps the open folder while it still exists.

Provider discovery also runs in the global config scope when no project exists. A fresh install can therefore choose models and save global session defaults before adding its first folder. Adding a folder activates a separate project scope and leaves the global selection intact.

Caches and async work must be scoped to the active runtime. A failed authoritative request must preserve existing state and remain distinguishable from a successful empty result.

`useWorktreeStore.refreshProject()` coalesces discovery by runtime and project, rejects stale runtime completions, and keeps linked-worktree arrays reference-stable when topology is unchanged. Successful discoveries stay fresh for 30 s (`WORKTREE_REFRESH_FRESHNESS_MS`): background callers skip the network entirely inside the window unless they pass `{ force: true }`, which explicit mutation refreshes (worktree create/remove, GitHub checkout flows, close-worktree) always do. Failures never count as fresh. `WorktreeDiscovery` refreshes with bounded concurrency on mount, on window focus / visibility-to-visible, and on a 60 s interval while the app is visible; hidden UI does no polling. The mount refresh fires only when the sorted project-path set (or runtime) actually changes, and focus/visibility passes go through the freshness window so rapid focus toggling costs nothing. Underneath, `/check` caches positive results for 5 minutes and negative results for 30 s (`GIT_REPO_CHECK_POSITIVE_TTL_MS` / `GIT_REPO_CHECK_NEGATIVE_TTL_MS`), and worktree lists cache for 10 s (`GIT_WORKTREES_CACHE_TTL_MS`); both have in-flight dedupe, both are keyed by runtime + directory and cleared on runtime switch, fetch failures are never cached, and worktree create/remove invalidates the topology (plus repo-check) entries it can affect.

`useGitStore.fetchBranches()` coalesces concurrent loads by runtime and directory; `fetchLog()` does the same keyed by runtime + directory + maxCount. Composer, dialog, and Git-surface mounts share one request; a runtime switch clears the in-flight owner so an old host cannot commit into the new store.

Git remount contract (Git is a singleton surface that remounts on every context-panel switch and restores from this store): a mount reads cache synchronously and revalidates in the background only when stale, so cached status/branches/log render immediately with no loading flash. Mount-time freshness windows (`ensureAll`, `STATUS_MOUNT_STALE_THRESHOLD` 15 s / `LOG_MOUNT_STALE_THRESHOLD` 30 s / `BRANCHES_MOUNT_STALE_THRESHOLD` 60 s) are deliberately longer than the background windows (`ensureStatus` 5 s, main-log 10 s, branches 30 s): a quick Git -> Terminal -> Files -> Git round-trip costs zero requests, while real changes still arrive promptly because in-app file saves, tool completions, and branch checkouts emit `requestGitRefresh` hints that force a fresh status fetch, and every mutation (stage/commit/merge/rebase/stash/revert) refreshes explicitly. Remotes + remote URL are cached per directory with a 5 min window (`REMOTES_STALE_THRESHOLD`, in-flight deduped by runtime + directory); the window is safe because the remote list changes only via remote add/remove, and remote-changing mutations must call `invalidateRemotes` (which marks the entry stale but keeps it visible). Ranged (branch-divider) and graph log queries are cached per (directory, from/to/all/file/maxCount) with the same 30 s log freshness and in-flight dedupe (`fetchLogQuery`, LRU-bounded to 10 entries per directory); the graph query runs only when its dialog opens, and explicit refresh passes `{ force: true }`. Diff prefetch skips cached/in-flight paths and stays gated on document visibility, so a remount with an unchanged change set issues zero file-diff requests. Every key includes the runtime key and resets on runtime switch; every failure preserves prior state (fetch failures never count as fresh) and never masquerades as empty — a remotes failure keeps the prior list (or null when never fetched), a log-query failure returns the prior entry (or null).

`useProjectsStore.resetForRuntimeSwitch()` clears project paths until the new
runtime's authenticated settings snapshot arrives; persisted paths from another
host are not a valid bootstrap source. `setActiveProjectIdOnly()` changes and
persists only the active pointer. It preserves the `projects` array and project
metadata references so session or worktree navigation does not wake every
project-list consumer.

When changing store shape, keep persisted state intentionally compatible or discard obsolete fields safely. Do not use persisted history to infer live Pi activity.
