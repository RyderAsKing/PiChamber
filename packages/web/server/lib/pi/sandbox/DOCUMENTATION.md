# Project sandboxes

## Purpose

A project can run its sessions in a separate Pi session daemon inside a sandbox (#242, tickets #243-#249). This module owns everything about that choice except the daemon itself: the launcher seam and the nono launcher, PiChamber's nono profile, a project's grants and setting, the manager that starts, routes, drains and stops sandbox daemons, the public sandbox routes, OAuth refresh on a sandbox's behalf, and the trust reset when a project leaves its sandbox. Nothing here runs unless a project's setting is `nono`: with no sandboxed project the server starts no sandbox daemon, probes nothing, and routes every request to the main daemon unchanged.

The daemon side (the supervisor launching a daemon through a launcher, launch identity and profile keys, liveness and stop, session leases across the boundary, the merged event stream, and `sessions.readPersisted`) is in `../session-daemon/DOCUMENTATION.md`, "Sandbox launchers".

## Ownership

- `launcher.js`: the launcher contract, grant and network validation, and launch identity.
- `nono-launcher.js`: the nono probe and the `nono run` command. `nono-profile.json`: PiChamber's static nono policy.
- `project-sandbox.js`: one project's grants, network, shadow Pi agent folder, and private temp folder (`prepareProjectSandbox`).
- `project-sandbox-setting.js`: the per-project `sandbox` setting and its normalization.
- `project-sandbox-manager.js`: registers sandbox daemons in the daemon pool and starts them lazily. It also answers the fail-closed and read-only fallbacks, drains sessions between daemons, replaces stale daemons, refreshes OAuth through the main daemon, resets trust when a project is switched off, and resolves git sandboxes (`gitSandboxForDirectory`).
- `sandbox-routes.js`: `/api/pi/sandbox` and `/api/pi/sandbox/projects`.
- `trust-ask.js`: the server-owned list of folders whose Pi trust must stay "ask".

The composition root (`packages/web/server/index.js`) creates the manager with the nono launcher, and passes the manager to the Pi routes (`../routes.js`).

## Behaviour and invariants

- Contract. A launcher has `id`, `platforms`, `transport: 'local-socket'`, `probe()`, `identity({ grants, network })`, and `prepare({ argv, env, cwd, grants, network, tmpDir })`. `prepare` returns `{ command, args, env }` that wraps `argv` unchanged. Grants are structured (`read`, `readWrite`, `readFile`, `readWriteFile`, `unixSocketBind`) with absolute paths, never raw user strings. Network is `{ mode: 'proxy', allowHosts, allowLocalPorts }` or `{ mode: 'none' }`. `launcher.js` validates both, de-duplicates grants, and sorts them, so the same request always gives the same command and identity.
- nono probe (`nono-launcher.js`). Linux only. macOS, Windows, and WSL2 (detected from `/proc/version`) report `UNSUPPORTED_PLATFORM` without running nono. Otherwise: binary missing is `NOT_INSTALLED`, unreadable `--version` output is `VERSION_UNKNOWN`, below 0.82.0 is `TOO_OLD`, and `nono setup --check-only` failing with "Landlock is not available" (or without a Landlock ABI line) is `NO_LANDLOCK`; any other failure is `SETUP_CHECK_FAILED`. Success reports the version and `landlock-abi-<n>`. `identity` and `prepare` refuse to run before a successful probe.
- nono command. `nono run -s --profile <nono-profile.json> --no-rollback --no-audit --no-diagnostics`, the grant flags (`--read`, `--allow`, `--read-file`, `--allow-file`, `--allow-unix-socket-dir-bind`), the network flags, then `--` and the daemon argv. Environment: the daemon's environment plus `NONO_NO_SAVE_PROMPT=1`, `NONO_NO_UPDATE_CHECK=1`, and `TMPDIR` set to the project's private temp folder. Network: each allowed host is `--allow-domain` (proxy mode); each local port is `--allow-connect-port`; with no allowed host and no port, or mode `none`, it is `--block-net`, because nono without a proxy or port rule leaves the network open. Ports 80 and 443 are refused (`SANDBOX_PORT_REFUSED`): a port grant applies to every host and bypasses the proxy.
- Profile. `nono-profile.json` holds only policy, close to nono's Pi profile: runtime and cache groups, `system_write_linux` excluded (it grants all of `/tmp`), `signal_mode: isolated`, `linux.af_unix_mediation: pathname` (without it the sandbox can connect to the main daemon's socket), and `workdir.access: none`. Every path is a per-launch flag. PiChamber never installs the nono Pi pack.
- Packaged desktop. The server package sits in `app.asar`, which the nono binary cannot read. When the profile path runs through an `.asar` archive, `createNonoLauncher({ stageDir })` copies the profile to `<stageDir>/nono-profile-<content hash>.json` (mode 0600, written through a temp file and renamed) and passes that path; a profile outside an archive is used in place. A failed copy is `SANDBOX_PROFILE_UNREADABLE`. The server passes `stageDir = <dataDir>/pi/sandbox`.
- Project grants (`prepareProjectSandbox`). Read-write: the project folder, `<dataDir>/worktree/<project id>/`, the private temp folder `<dataDir>/pi/sandbox/<project key>/tmp`, the shadow agent folder `<dataDir>/pi/sandbox/<project key>/agent`, the real Pi session folder of the project and of each worktree passed in, and the session lease folder. Read: the runtime (the real Node install prefix, or the Electron app folder), the PiChamber install and the outer `node_modules` holding the Pi SDK, and the existing Pi resource folders (`extensions`, `prompts`, `themes`, `skills`, `tools`, `bin`). Read single files: the existing `settings.json`, `auth.json`, `models.json`, `trust.json`, `mcp.json`. User extras are folders, read or read-write; one that overlaps the PiChamber data folder or the Pi agent folder is refused (`SANDBOX_GRANT_REFUSED`). Local ports also refuse the server's own port. Never granted: the data folder as a whole, other daemons' profile folders and credentials, other projects' session folders, or the `sessions/` parent.
- Shadow agent folder. Pi takes a lock folder beside `settings.json` and `auth.json` even to read them, and loads no credentials from a read-only agent folder. The sandbox daemon gets `--agent-dir` pointing at the shadow folder, which holds symlinks to the real config files and resource folders, to the project's real session folders, and to the real lease folder. Lock folders land in the shadow; writes to the real config fail. Preparing again repoints links and never deletes a real file or folder found where a link belongs (`SANDBOX_SHADOW_CONFLICT`).
- Setting (`project-sandbox-setting.js`). A project entry's `sandbox` field is `{ mode: 'off' | 'nono', allowHosts, allowLocalPorts, extraFolders: [{ path, access: 'read' | 'readWrite' }] }`, normalized and bounded (64 hosts, 32 ports, 32 folders; ports 80 and 443 and relative folders are refused as `INVALID_SANDBOX_SETTING`). It is host-local: it lives in the runtime state file (`../ui-settings-store.js`, `setProjectSandbox`), never in portable settings. A client's settings write cannot set, change, or drop it; the store carries the current value over by project id. A malformed stored value counts as sandboxed and unavailable, never as off.
- Manager (`project-sandbox-manager.js`). `reconcile()` reads the projects and registers `sandbox:<project id>` in the pool for each `nono` project, owning the project root and its worktree root `<dataDir>/worktree/<git project id>` (the id from `<project>/.git/pichamber`, accepted only as 40 or 64 hex characters because a sandboxed agent can write that file). It runs at server start and after each settings write and setting change, and retires the daemons of projects no longer sandboxed (see Switching below). A registered daemon starts lazily on its first command: probe (cached until `recheck`), `providers.hosts` from the main daemon (hosts of signed-in providers' model base URLs) merged into the project's allowed hosts, `prepareProjectSandbox`, the per-daemon intake, then the supervisor; concurrent first commands share one start. An idle daemon (`runtime.health` `residentSessions` 0 for 10 minutes) is stopped and restarts on the next command; passive reads (`sessions.list`, `sessions.pendingInput`, `sessions.sendReceipt`) neither start one nor count as activity.
- Fail closed. A sandboxed project's Pi runtime never starts outside its sandbox. A failed probe, provider-host lookup, prepare, or start fails the request as HTTP 503 `SANDBOX_UNAVAILABLE` with `reason` (the launcher reason code, `PROVIDER_HOSTS_UNAVAILABLE`, or the start error's code), and is retried on the next command. Some reads still answer without the sandbox, because none of them runs Pi code: `sessions.list` and `archive.publish` go to the main daemon whenever the project's daemon is not running (see List fallback), and `sessions.open` and `sessions.messages` fall back to the main daemon's `sessions.readPersisted` when the sandbox fails to start with `SANDBOX_UNAVAILABLE` (see Read-only transcripts). Every other command fails closed, including prompt, steer, follow-up, bash, navigate, fork, compact, model and thinking changes, `sessions.tree`, and extension responses. Commands that name only a session id (no directory) are routed by the cwd in that session's JSONL header whenever any project is sandboxed.
- Read-only transcripts. While a project's sandbox cannot start, opening one of its sessions (`GET /api/pi/sessions/:id`, `/snapshot`, `/messages`) is answered by the main daemon's `sessions.readPersisted` (`../session-daemon/DOCUMENTATION.md`). That command parses the JSONL into an in-memory Pi session manager and projects it like `sessions.open`. It starts no runtime, extension, or tool, takes no lease, and writes nothing. The manager drops any `streamEpoch` or `inputState` from the answer and marks it `readOnly: true`. The detail is idle with `lastSequence: -1` and no extension or bash state, and the route stamps it with the project's `stream`. The UI commits it as history without binding the session to that stream (`packages/ui/src/sync/DOCUMENTATION.md`). A send to the session still goes to the sandbox and fails with `SANDBOX_UNAVAILABLE`. A sandbox that is merely stopped (idle) is started by opening, as before; only a failed start falls back. Tests: `../routes-sandbox.test.js` and `../session-daemon/session-daemon-read-persisted.test.js`.
- List fallback. When the main daemon answers `sessions.list` for a sandboxed project whose daemon is not running, the rows lose `live`, `inputState`, and the top-level `streamEpoch`: that state is the main daemon's, not the sandbox stream's. The response still names the project's `stream` and its rows keep `sandboxed: true` (opening one runs in the sandbox, or reads it read-only while the sandbox cannot start), so clients list those rows as metadata only.
- Routes (`sandbox-routes.js`). `GET /api/pi/sandbox` and `POST /api/pi/sandbox/recheck` return `{ launchers: [{ id, available, version? | reason? }] }`. `GET /api/pi/sandbox/projects` returns `{ projects: [{ projectId, mode, launcher, availability: { state: 'off' | 'available' | 'unavailable', reason? }, allowHosts, allowLocalPorts, extraFolders }] }`, without project paths. `PUT /api/pi/sandbox/projects/:projectId` replaces one setting and returns `{ project }`; errors are 400 `INVALID_SANDBOX_SETTING`, 404 `PROJECT_NOT_FOUND`. Session rows, details, and created, forked, or cloned sessions in a sandboxed project carry `session.sandboxed: true`.
- Switching (#247). Every move of a project's sessions between daemons drains: the old daemon stays registered under its own key while the new one owns the folders. Turning a project on drains the main daemon's sessions in it; turning it off (or removing the project) retires the sandbox daemon into the main daemon; a changed setting retires the running sandbox daemon into a new one under `sandbox:<project id>:<generation>`. A retired daemon is re-registered with `directories: []` and named by `setDraining` for the folders. The manager polls `sessions.release` on it at once and then every second: each released session, and each pending one that vanished, gets `announceMove` (clients reset and refetch it). When nothing is pending, the drain clears `setDraining`, stops the old daemon (and its intake), and unregisters it. `DAEMON_UNAVAILABLE` or three failed polls also end the drain. A running turn is never cut off.
- Pending sessions. While a session is pending in a draining daemon, session rows and details carry `pendingSwitch: { to: 'nono' | 'off' }` (only when the drain is a setting switch, not a staleness replacement) and `sandboxed` reflects the daemon running it now. `drainingSession(id)` routes these commands to the old daemon: `sessions.open`, messages, tree, abort, abortBash, steer, `sessions.sendReceipt`, `extensions.draft`, and `extensions.custom.*`; responses carry the old daemon's `stream`. Any other command (prompt, followUp, model, fork, ...) fails with HTTP 409 `SESSION_IN_USE` until the turn ends. `extensions.respond` falls back to the folder's draining daemons when the owner does not hold the request.
- Old epochs after a move. A client that sends right after `session.moved` may still hold the old daemon's `streamEpoch`. The manager remembers the epoch each moved session had (2 minutes, at most 4096 sessions); a send or send receipt carrying exactly that epoch is rewritten to the new daemon's current epoch. Any other mismatch still fails as before.
- Staleness. Single-file grants (`settings.json`, `auth.json`, `models.json`, `trust.json`, `mcp.json`) pin the file the daemon saw at launch; an atomic replace leaves the sandbox reading the old one. The manager records a fingerprint (device, inode, size, mtime of each file) and the granted worktree list at launch. On each idle tick, after every route that writes Pi config through the main daemon (`providers.models.set/add`, `settings.set`, logout, and login once its state is `complete`), and before a request into a worktree the daemon was not granted, it compares them; a change retires the daemon at once into a fresh one (a drain, so busy sessions finish first). A request into an ungranted worktree waits for the new daemon.
- OAuth. A sandbox daemon reads `auth.json` but cannot write it, so it cannot refresh an expiring token. Before each sandbox start the manager asks the main daemon for `providers.oauth.refresh` with 30 minutes of minimum validity (single-flight). The proactive refresh is a deliberate deviation from #242, which only asks that token refreshes keep sandboxed sessions working. Pi refreshes inside a token's last five minutes, which a sandbox cannot do, so refreshing ahead of time keeps a running sandbox from meeting an expired token mid-turn. A failed refresh does not stop the start: the sandbox may use API keys or still-valid tokens, and a turn that needs an expired token fails visibly in its chat. The manager logs a warning with the error code only, never a token or Pi's message. A sandbox `session.error` frame matching Pi's "OAuth refresh failed for <provider>" or "Credential store modify failed for <provider>" (pi-ai's `refreshStoredOAuthCredential`) triggers the same refresh, then the staleness check, so the new token reaches a fresh daemon. `../routes-sandbox.test.js` produces both messages with the installed pi-ai, so an upstream rewording fails a test.
- Trust after turning off. Code that ran inside the sandbox may have trusted the project. Turning a project off (or removing it) resets Pi trust for its root and worktrees to unset (`settings.set` `trust: null`), and adds them to the server-owned trust-ask list (`trust-ask.js`, `<dataDir>/pi/trust-ask.json`, mode 0600, at most 4096 folders). The daemon's automatic trust of known folders skips any folder in or under a listed one (`createSessionDaemon({ isTrustAskDirectory })`; an unreadable or malformed list counts as listing every folder), so Pi asks again. An explicit trust decision through `settings.set` removes the folder from the list. A failed reset is retried on the next idle tick.
- Scope. Only Pi session daemons (the agent) run in the sandbox. PiChamber's own Git panel, terminal, browser and GitHub features, and worktree hooks and start commands, run outside it with the user's access, so git config, hooks or filters an agent writes into the repo can run when the user or the Git panel runs git. This is a known, accepted trade-off. Git for every folder runs as it does without a sandbox.
- Open requests. Each sandbox daemon gets its own `<runtime folder>/open-url.sock`. The manager starts an intake on that socket before the daemon (`../../open-url/intake.js`) that publishes through that daemon's `openUrl.publish`, and stops it with the daemon.
