# Project sandboxes

## Purpose

A project can run its sessions in a separate Pi session daemon inside a sandbox (#242, tickets #243-#249). This module owns everything about that choice except the daemon itself: the launcher seam and the nono launcher, PiChamber's nono profile, a project's grants and setting, the manager that starts, routes, drains and stops sandbox daemons, the public sandbox routes, OAuth refresh on a sandbox's behalf, and the trust reset when a project leaves its sandbox. Nothing here runs unless a project is sandboxed (its setting is `nono`, or `default` while the host default is on): with no sandboxed project the server starts no sandbox daemon, probes nothing, and routes every request to the main daemon unchanged.

The daemon side (the supervisor launching a daemon through a launcher, launch identity and profile keys, liveness and stop, session leases across the boundary, the merged event stream, and `sessions.readPersisted`) is in `../session-daemon/DOCUMENTATION.md`, "Sandbox launchers".

## Ownership

- `launcher.js`: the launcher contract, grant and network validation, and launch identity.
- `nono-launcher.js`: the nono probe and the `nono run` command. `nono-profile.json`, `nono-profile-wsl2.json`, `nono-profile-macos.json`: PiChamber's static nono policy for each host kind.
- `project-sandbox.js`: one project's grants, network, shadow Pi agent folder, and private temp folder (`prepareProjectSandbox`).
- `project-sandbox-setting.js`: the per-project `sandbox` setting and its normalization.
- `project-sandbox-manager.js`: registers sandbox daemons in the daemon pool and starts them lazily. It also answers the fail-closed and read-only fallbacks, drains sessions between daemons, replaces stale daemons, refreshes OAuth through the main daemon, resets trust when a project is switched off.
- `sandbox-routes.js`: `/api/pi/sandbox` (status and `recheck`), `/api/pi/sandbox/projects`, and `/api/pi/sandbox/defaults`.
- `worktree-ids.js`: the remembered worktree folder id of each sandboxed project.
- `trust-ask.js`: the server-owned list of folders whose Pi trust must stay "ask".
- `sandboxed-folders.js`: the server-owned record of the folders sandbox daemons own, which the main daemon reads before it starts a runtime.

The composition root (`packages/web/server/index.js`) creates the manager with the nono launcher, and passes the manager to the Pi routes (`../routes.js`).

## Behaviour and invariants

- Contract. A launcher has `id`, `platforms`, `transport: 'local-socket'`, `probe()` (`{ available: true, version, capabilities, limits? }` or `{ available: false, code }`), `identity({ grants, network })`, and `prepare({ argv, env, cwd, grants, network, tmpDir })`. `prepare` returns `{ command, args, env }` that wraps `argv` unchanged. Grants are structured (`read`, `readWrite`, `readFile`, `readWriteFile`, `unixSocketBind`) with absolute paths, never raw user strings. Network is `{ mode: 'proxy', allowHosts, allowLocalPorts }` or `{ mode: 'none' }`. An allowed host is a public name: at least two labels (two after a `*.` wildcard), at most 253 characters and 63 per label, not `localhost`, `*.localhost` or `*.local`, and no last label starting with a digit (any IP literal); anything else is `SANDBOX_INVALID_NETWORK`, because the PiChamber server listens on the same machine. `launcher.js` validates both, de-duplicates grants, and sorts them, so the same request always gives the same command and identity.
- nono probe (`nono-launcher.js`). The host kind comes first: `darwin` is macOS, and `linux` is WSL2 when `/proc/version` names Microsoft or WSL, otherwise Linux. Any other platform is `UNSUPPORTED_PLATFORM` without running nono. Then: binary missing is `NOT_INSTALLED`, unreadable `--version` output is `VERSION_UNKNOWN`, below 0.82.0 is `TOO_OLD`. On Linux and WSL2, `nono setup --check-only` failing with "Landlock is not available" (or without a Landlock ABI line) is `NO_LANDLOCK`, and on WSL2 an ABI below V4 is `WSL_KERNEL_TOO_OLD` (no TCP rules, so nothing holds the sandbox to nono's proxy; `wsl --update` fixes it). On macOS the check must exit 0 and print "Seatbelt sandbox support verified". Any other failure is `SETUP_CHECK_FAILED`. Success reports the version, `landlock-abi-<n>` or `seatbelt`, and the host's `limits` when it has any. `identity` and `prepare` refuse to run before a successful probe, and use the profile of the probed host kind, so the same request has a different identity on each.
- Host limits. A limit is a rule the sandbox cannot enforce on this host (`SANDBOX_LIMIT_CODES` in `launcher.js`). WSL2 has `UNIX_SOCKETS`: nono's `af_unix_mediation` needs seccomp user notification, WSL2's init already holds the only listener, and nono refuses to start with the setting, so the WSL2 profile leaves it out. Pathname Unix sockets are then reachable from inside the sandbox, and code there can ask a local service (the systemd user manager, D-Bus, an SSH or GPG agent, Docker) to act outside it. The main daemon's socket still requires its credential, which the sandbox cannot read. WSL2 also has `PROXY_PORT`: Landlock filters TCP by port only, and the seccomp check that holds the proxy's port to the proxy on Linux is missing, so code in the sandbox can connect to any host on that port (checked by hand on a WSL2 6.18 kernel: `1.1.1.1:<proxy port>` was not refused, `1.1.1.1:443` was). A server listening on every port can therefore receive data, whatever the allowed hosts say. Files stay limited, and with no allowed host (`--block-net`) the network is fully blocked. The owner accepts a host's limits in the host default (`acceptedLimits`); until every reported limit is accepted, every sandboxed project is unavailable with `SANDBOX_LIMITS_NOT_ACCEPTED` and no sandbox starts. Withdrawing acceptance retires running sandbox daemons (a drain, so a running turn finishes) and the next command fails closed. Linux and macOS have no limits.
- nono command. `nono run -s --profile <nono-profile.json> --no-rollback --no-audit --no-diagnostics`, the grant flags (`--read`, `--allow`, `--read-file`, `--allow-file`, `--allow-unix-socket-dir-bind`), the network flags, then `--` and the daemon argv. Environment: the daemon's environment plus `NONO_NO_SAVE_PROMPT=1`, `NONO_NO_UPDATE_CHECK=1`, and `TMPDIR` set to the project's private temp folder. Network: each allowed host is `--allow-domain` (proxy mode). On Linux and WSL2 each local port is `--allow-connect-port`, and with no allowed host and no port, or mode `none`, it is `--block-net`, because nono without a proxy or port rule leaves the network open. Ports 80 and 443 are refused (`SANDBOX_PORT_REFUSED`): on Linux a port grant applies to every host and bypasses the proxy. macOS: nono refuses `--allow-connect-port` (Seatbelt cannot filter TCP by port), so each local port is `--open-port`, which allows that port on localhost only; with no allowed host it adds `--block-net`, which keeps those localhost rules. Seatbelt cannot limit binding or inbound connections by port either, so any port grant on macOS also lets the sandbox listen on any port.
- Profiles. Each holds only policy, close to nono's Pi profile: runtime and cache groups, `signal_mode: isolated`, and `workdir.access: none`. `nono-profile.json` (Linux) excludes `system_write_linux` (it grants all of `/tmp`) and sets `linux.af_unix_mediation: pathname` (without it the sandbox can connect to any Unix socket it can name, including the main daemon's). `nono-profile-wsl2.json` is the same without `af_unix_mediation` (see Host limits). `nono-profile-macos.json` excludes `system_write_macos` (all of `/tmp` and `/var/folders`) and adds the macOS cache group; Seatbelt starts proxy and blocked modes from `deny network*` and allows only Unix sockets granted by flag. Every path is a per-launch flag. PiChamber never installs the nono Pi pack.
- Packaged desktop. The server package sits in `app.asar`, which the nono binary cannot read. When a profile path runs through an `.asar` archive, `createNonoLauncher({ stageDir })` copies that profile to `<stageDir>/nono-profile-<content hash>.json` (mode 0600, written through a temp file and renamed) and passes that path; a profile outside an archive is used in place. A failed copy is `SANDBOX_PROFILE_UNREADABLE`. The server passes `stageDir = <dataDir>/pi/sandbox`.
- Project grants (`prepareProjectSandbox`). Read-write: the project folder, `<dataDir>/worktree/<project id>/`, the private temp folder `<dataDir>/pi/sandbox/<project key>/tmp`, the shadow agent folder `<dataDir>/pi/sandbox/<project key>/agent`, the real Pi session folder of the project and of each worktree passed in, and the session lease folder. Read: the runtime (the real Node install prefix, or the Electron app folder), the PiChamber install and the outer `node_modules` holding the Pi SDK, and the existing Pi resource folders (`extensions`, `prompts`, `themes`, `skills`, `tools`, `bin`). Read single files: the existing `settings.json`, `auth.json`, `models.json`, `trust.json`, `mcp.json`. User extras are folders, read or read-write; one that overlaps the PiChamber data folder or the Pi agent folder is refused (`SANDBOX_GRANT_REFUSED`), checked by both its written path and its real path, so a symlink cannot reach them. The project folder itself is refused the same way when it contains either folder or sits inside one (a worktree under `<dataDir>/worktree` is the exception). Local ports also refuse the server's own port. Never granted: the data folder as a whole, other daemons' profile folders and credentials, other projects' session folders, or the `sessions/` parent.
- Shadow agent folder. Pi takes a lock folder beside `settings.json` and `auth.json` even to read them, and loads no credentials from a read-only agent folder. The sandbox daemon gets `--agent-dir` pointing at the shadow folder, which holds symlinks to the real config files and resource folders, to the project's real session folders, and to the real lease folder. Lock folders land in the shadow; writes to the real config fail. Preparing again repoints links and never deletes a real file or folder found where a link belongs (`SANDBOX_SHADOW_CONFLICT`).
- Setting (`project-sandbox-setting.js`). A project entry's `sandbox` field is `{ mode: 'off' | 'nono', allowHosts, allowLocalPorts, extraFolders: [{ path, access: 'read' | 'readWrite' }] }`, normalized and bounded (64 hosts, 32 ports, 32 folders; ports 80 and 443 and relative folders are refused as `INVALID_SANDBOX_SETTING`). It is host-local: it lives in the runtime state file (`../ui-settings-store.js`, `setProjectSandbox`), never in portable settings. A client's settings write cannot set, change, or drop it; the store carries the current value over by project id. A malformed stored value counts as sandboxed and unavailable, never as off. `mode: 'default'`, or no `sandbox` field, follows the host default.
- Host default (`normalizeSandboxDefaults`, `readSandboxDefaults`). The runtime state file's `sandboxDefaults` is `{ mode: 'off' | 'nono', allowHosts, acceptedLimits }` (64 hosts at most; `acceptedLimits` lists known limit codes, see Host limits), set only through `setSandboxDefaults`; like a project's setting, a client's settings write and a legacy portable file cannot set it. Missing means off, so projects with no setting keep running unsandboxed until someone turns the default on. `effectiveProjectSandbox(project, settings)` is the one place that decides: an explicit `off` is off whatever the default says; `nono`, or `default` while the default is on, is sandboxed with `allowHosts` = default hosts + the project's own, and its own ports and folders. An unreadable default sandboxes every project that follows it as unavailable; an unreadable project setting does the same for that project. Changing the default's hosts changes every sandboxed project's setting key, so running daemons are retired into new ones.
- Manager (`project-sandbox-manager.js`). `reconcile()` reads the projects and registers `sandbox:<project id>` in the pool for each `nono` project, owning the project root (as stored and as its real path) and its worktree root `<dataDir>/worktree/<git project id>` (see Worktree ids). It runs at server start and after each settings write and setting change, and retires the daemons of projects no longer sandboxed (see Switching below). Passes run one at a time, in the order they were asked for: two overlapping passes working from different settings would undo each other's registrations. A pass that removes an entry unregisters its pool key only while that entry's runtime still holds it, and a project turned on again while its old daemon drains takes the next free `sandbox:<project id>:<generation>` key. A registered daemon starts lazily on its first command: probe (cached until `recheck`), `providers.hosts` from the main daemon (hosts of signed-in providers' model base URLs) merged into the project's allowed hosts (a provider host `normalizeNetwork` would refuse, such as a bare or `.local` name, is left out and logged by count), `prepareProjectSandbox`, the per-daemon intake, then the supervisor; concurrent first commands share one start. An idle daemon (`runtime.health` `residentSessions` 0 for 10 minutes) is stopped and restarts on the next command; passive reads (`sessions.list`, `sessions.pendingInput`, `sessions.sendReceipt`) neither start one nor count as activity.
- Worktree ids (`worktree-ids.js`). `<project>/.git/pichamber` names the project's worktree folder, and a sandboxed agent can rewrite or delete it. The manager takes the id from that file only the first time it sees one for a project root (40 or 64 hex characters), and records it in `<dataDir>/pi/sandbox/worktree-ids.json` (mode 0600, at most 4096 projects), which no sandbox can write. From then on the remembered id decides the worktree root the project's daemon owns and is granted, across restarts and whatever the file says. A project sandboxed before it had a worktree has no id yet: the first request into an unowned folder under `<dataDir>/worktree/` reconciles, so the id written with the first worktree is picked up before that request is routed. An unreadable record keeps the ids already in memory and is logged. Known limit: the id is trusted on first use, so an agent that writes the file before the project has any worktree chooses the (hex) folder name. The git service (`../../git/service.js`) recomputes the id when the file does not hold a hex id.
- Routing. While any project is sandboxed, every folder a client names is spelled the way the daemon will read it before a daemon is chosen (`routeDirectory`: trimmed, `~` as the home folder, resolved); a spelling that reaches a sandboxed project or worktree through a symlink routes to that project, and a path that is not absolute is refused with 400 `INVALID_ARGUMENT`, since the pool would give it to the main daemon. A persisted session is routed by where its transcript is stored (`directoryForSession`): a transcript in the session folder of a sandboxed project or of one of its worktrees belongs to that project whatever `cwd` its header names, because the sandboxed agent can rewrite the header but cannot move the file out of the folders it was granted. Only a transcript stored elsewhere is routed by its header.
- Unapplied settings. A reconcile that fails leaves the pool possibly short of a sandboxed project, so the manager reports `needsReconcile()`. The Pi routes then retry it before each `/api/pi` request and, while it still fails, answer 503 `SANDBOX_UNAVAILABLE` with reason `SANDBOX_SETTINGS_UNREADABLE` instead of using the main daemon. `/api/pi/ui-settings`, `/api/pi/sandbox*` and `/api/pi/events` stay open so the cause can be seen and fixed. This covers a failed reconcile at server start as well as one after a save.
- Fail closed. A sandboxed project's Pi runtime never starts outside its sandbox. A failed probe, provider-host lookup, prepare, or start fails the request as HTTP 503 `SANDBOX_UNAVAILABLE` with `reason` (the launcher reason code, `PROVIDER_HOSTS_UNAVAILABLE`, or the start error's code), and is retried on the next command. A sandbox daemon gets 45 s to report ready (the main daemon 15 s), since nono's setup and proxy add to its start. `POST /api/pi/sandbox/recheck` also forgets each stopped project's last start failure, so a one-off timeout does not leave the project shown as unavailable; its next command starts it again. Some reads still answer without the sandbox, because none of them runs Pi code: `sessions.list` and `archive.publish` go to the main daemon whenever the project's daemon is not running (see List fallback), and `sessions.open` and `sessions.messages` fall back to the main daemon's `sessions.readPersisted` when the sandbox fails to start with `SANDBOX_UNAVAILABLE` (see Read-only transcripts). Every other command fails closed, including prompt, steer, follow-up, bash, navigate, fork, compact, model and thinking changes, `sessions.tree`, and extension responses. Commands that name only a session id (no directory) are routed by the cwd in that session's JSONL header whenever any project is sandboxed.
- Main daemon stays out. The manager writes every folder a sandbox daemon owns (project root, its real path, its worktree root) to `<dataDir>/pi/sandboxed-folders.json` (mode 0600, at most 4096 folders) at the end of each reconcile and right after projects leave the sandbox; a failed write fails the reconcile, so routes stay closed. The supervisor starts only the main daemon with `--sandboxed-folders-file`. That daemon checks the record, by written and real path, before it creates any Pi runtime and refuses with `DIRECTORY_SANDBOXED`; a missing record lists nothing and an unreadable one counts as every folder. A request that names no folder while the active folder is sandboxed, and a catalog read that names a sandboxed folder (`providers.refresh`, `resources.list`, `extensions.list`, prompt-mutation services), is answered from a folder outside every sandbox: the daemon's startup folder, or the Pi agent folder. Runtimes the main daemon already runs in a newly sandboxed folder keep running until the drain releases them. Routes send changes to a project's own prompts and instruction files (`resources.update`, `resources.prompts.*` with a folder) to the daemon that owns the folder; creating a global prompt stays with the main daemon, since a sandbox cannot write Pi's agent folder.
- Read-only transcripts. While a project's sandbox cannot start, opening one of its sessions (`GET /api/pi/sessions/:id`, `/snapshot`, `/messages`) is answered by the main daemon's `sessions.readPersisted` (`../session-daemon/DOCUMENTATION.md`). That command parses the JSONL into an in-memory Pi session manager and projects it like `sessions.open`. It starts no runtime, extension, or tool, takes no lease, and writes nothing. The manager drops any `streamEpoch` or `inputState` from the answer and marks it `readOnly: true`. The detail is idle with `lastSequence: -1` and no extension or bash state, and the route stamps it with the project's `stream`. The UI commits it as history without binding the session to that stream (`packages/ui/src/sync/DOCUMENTATION.md`). A send to the session still goes to the sandbox and fails with `SANDBOX_UNAVAILABLE`. A sandbox that is merely stopped (idle) is started by opening, as before; only a failed start falls back. Tests: `../routes-sandbox.test.js` and `../session-daemon/session-daemon-read-persisted.test.js`.
- List fallback. When the main daemon answers `sessions.list` for a sandboxed project whose daemon is not running, the rows lose `live`, `inputState`, and the top-level `streamEpoch`: that state is the main daemon's, not the sandbox stream's. The response still names the project's `stream` and its rows keep `sandboxed: true` (opening one runs in the sandbox, or reads it read-only while the sandbox cannot start), so clients list those rows as metadata only.
- Routes (`sandbox-routes.js`). `GET /api/pi/sandbox` and `POST /api/pi/sandbox/recheck` return `{ launchers: [{ id, available, version? | reason?, limits?, limitsAccepted? }] }`. `GET /api/pi/sandbox/projects` returns `{ projects: [{ projectId, mode, launcher, availability: { state: 'off' | 'available' | 'unavailable', reason? }, allowHosts, allowLocalPorts, extraFolders }] }`, without project paths. Each project also carries `choice` (`default`, `off` or `nono`, its own setting; `mode` is what it runs with after the default) and only its own hosts. `GET /api/pi/sandbox/defaults` returns `{ defaults: { mode, allowHosts, acceptedLimits, invalid? } }`; `PUT` takes any of `mode`, `allowHosts` and `acceptedLimits` (none is 400 `INVALID_SANDBOX_SETTING`, and so is an unknown limit code); a field left out keeps its stored value, merged under the settings store lock, so a page that only edits hosts cannot undo a mode or acceptance set elsewhere. It saves, reconciles, and returns `{ defaults, projects }`, since every project that follows it may have changed. A save that was stored answers 200 even when applying it failed; the apply is retried before the next Pi request (see Unapplied settings). `PUT /api/pi/sandbox/projects/:projectId` replaces one setting (mode `default`, `off` or `nono`) and returns `{ project }`; errors are 400 `INVALID_SANDBOX_SETTING`, 404 `PROJECT_NOT_FOUND`. Session rows, details, and created, forked, or cloned sessions in a sandboxed project carry `session.sandboxed: true`.
- Switching (#247). Every move of a project's sessions between daemons drains: the old daemon stays registered under its own key while the new one owns the folders. Turning a project on (itself or through the default) drains the main daemon's sessions in it; turning it off (or removing the project) retires the sandbox daemon into the main daemon; a changed setting retires the running sandbox daemon into a new one under `sandbox:<project id>:<generation>`. A retired daemon is re-registered with `directories: []` and named by `setDraining` for the folders. The manager polls `sessions.release` on it at once and then every second: each released session, and each pending one that vanished, gets `announceMove` (clients reset and refetch it). When nothing is pending, the drain clears `setDraining`, stops the old daemon (and its intake), and unregisters it. `DAEMON_UNAVAILABLE` also ends the drain, and so do failed polls in a row: three when nothing is pending, sixty (about a minute) while a session is still pending, so a short stall does not cut off a running turn. A launch keeps the setting it started with: if the setting changes while the daemon starts, the launch stays under its own key and the request fails with `SANDBOX_SETTING_CHANGED` instead of running under the new key with old grants.
- Pending sessions. While a session is pending in a draining daemon, session rows and details carry `pendingSwitch: { to: 'nono' | 'off' }` (only when the drain is a setting switch, not a staleness replacement) and `sandboxed` reflects the daemon running it now. `drainingSession(id)` routes these commands to the old daemon: `sessions.open`, messages, tree, abort, abortBash, steer, `sessions.sendReceipt`, `extensions.draft`, and `extensions.custom.*`; responses carry the old daemon's `stream`. Any other command (prompt, followUp, model, fork, ...) fails with HTTP 409 `SESSION_IN_USE` until the turn ends. `extensions.respond` falls back to the folder's draining daemons when the owner does not hold the request.
- Old epochs after a move. A client that sends right after `session.moved` may still hold the old daemon's `streamEpoch`. The manager remembers the epoch each moved session had (2 minutes, at most 4096 sessions); a send or send receipt carrying exactly that epoch is rewritten to the new daemon's current epoch. Any other mismatch still fails as before.
- Staleness. Single-file grants (`settings.json`, `auth.json`, `models.json`, `trust.json`, `mcp.json`) pin the file the daemon saw at launch; an atomic replace leaves the sandbox reading the old one. The manager records a fingerprint (device, inode, size, mtime of each file) and the granted worktree list at launch. On each idle tick, after every route that writes Pi config through the main daemon (`providers.models.set/add`, `settings.set`, logout, and login once its state is `complete`), and before a request into a worktree the daemon was not granted, it compares them; a change retires the daemon at once into a fresh one (a drain, so busy sessions finish first). A request into an ungranted worktree waits for the new daemon.
- OAuth. A sandbox daemon reads `auth.json` but cannot write it, so it cannot refresh an expiring token. Before each sandbox start the manager asks the main daemon for `providers.oauth.refresh` with 30 minutes of minimum validity (single-flight). That call and `providers.hosts` pass every sandboxed folder as `exclude`, so the main daemon never starts a runtime in one to answer them. The proactive refresh is a deliberate deviation from #242, which only asks that token refreshes keep sandboxed sessions working. Pi refreshes inside a token's last five minutes, which a sandbox cannot do, so refreshing ahead of time keeps a running sandbox from meeting an expired token mid-turn. A failed refresh does not stop the start: the sandbox may use API keys or still-valid tokens, and a turn that needs an expired token fails visibly in its chat. The manager logs a warning with the error code only, never a token or Pi's message. A sandbox `session.error` frame matching Pi's "OAuth refresh failed for <provider>" or "Credential store modify failed for <provider>" (pi-ai's `refreshStoredOAuthCredential`) triggers the same refresh, then the staleness check, so the new token reaches a fresh daemon. `../routes-sandbox.test.js` produces both messages with the installed pi-ai, so an upstream rewording fails a test.
- Trust after turning off. Code that ran inside the sandbox may have trusted the project. Turning a project off (or removing it) resets Pi trust for its root and worktrees to unset (`settings.set` `trust: null`), and adds them to the server-owned trust-ask list (`trust-ask.js`, `<dataDir>/pi/trust-ask.json`, mode 0600, at most 4096 folders; a full list refuses the new folder with `TRUST_ASK_FULL` instead of dropping an older one). The daemon's automatic trust of known folders skips any folder in or under a listed one (`createSessionDaemon({ isTrustAskDirectory })`; an unreadable or malformed list counts as listing every folder), so Pi asks again. An explicit trust decision through `settings.set` removes the folder from the list. A failed reset is retried on the next idle tick. Unsetting trust and adding the folder to the list are retried separately: when only the list write failed, the retry does not unset trust again, so a decision the user made in between is kept.
- Scope. Only Pi session daemons (the agent) run in the sandbox. PiChamber's own Git panel, terminal, browser and GitHub features, and worktree hooks and start commands, run outside it with the user's access, so git config, hooks or filters an agent writes into the repo can run when the user or the Git panel runs git. This is a known, accepted trade-off. Git for every folder runs as it does without a sandbox.
- Open requests. Each sandbox daemon gets its own `<runtime folder>/open-url.sock`. The manager starts an intake on that socket before the daemon (`../../open-url/intake.js`) that publishes through that daemon's `openUrl.publish`, and stops it with the daemon.

## Tests

- `nono-launcher.test.js`: probe codes and host kinds, the profile for each, and the macOS port flags.
- `launcher.test.js`: host and port validation.
- `trust-ask.test.js`: the trust-ask list.
- `worktree-ids.test.js`: the remembered worktree ids.
- `sandboxed-folders.test.js`: the sandboxed folder record and the main daemon's reader.
- `../routes-sandbox.test.js`: routing, fail closed, read-only transcripts, switching, staleness, OAuth, trust reset, overlapping saves, forged transcript headers, path spellings, worktree ids, and unapplied settings.
- `../session-daemon/supervisor-sandbox.test.js` and `../session-daemon/supervisor-sandbox-nono.e2e.test.js`: the launched command and socket path limits. The e2e test runs the daemon under real nono and checks from inside the sandbox what it can reach: the project, other folders and sessions, Pi's config, the main credential, a loopback TCP server, a granted local port, and a Unix socket outside (reachable only on WSL2). It skips when the probe says nono cannot run; `PICHAMBER_REQUIRE_NONO_E2E=1` makes that a failure.
- CI. GitHub's Linux runners have no Landlock, so the Linux and WSL2 paths are run by hand on a Landlock host. `.github/workflows/sandbox-macos.yml` runs the e2e test on macOS with a checksum-verified nono release whenever this folder or `../session-daemon` changes.
