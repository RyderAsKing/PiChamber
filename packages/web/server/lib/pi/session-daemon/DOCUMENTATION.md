# Pi Session Daemon

## Purpose

This module is the Pi-owned session-daemon foundation. A detached local daemon process creates an `AgentSessionRuntime` with the Pi SDK, tracks it in a registry keyed by Pi session identity and cwd, keeps it behind a private local socket, and maps a small event subset to the PiChamber IPC contract. Browsers never connect to it. Directory inputs must be absolute except for the exact `~` global-session sentinel, which the daemon expands to the server user's home directory before validation. Other relative paths remain invalid.

## Entrypoints

- `../extension-protocol.js` owns the bounded form descriptor and response validation shared by the private daemon bridge and public route projection, so both sides of the IPC seam accept the same field contract.
- `extension-bridge.js` owns extension UI bindings, pending dialog lifecycle, normalized status/widget/panel/app state, snapshot projection, and extension event publication. `session-daemon.js` supplies runtime lookup, publication, redaction, and directory dependencies through its narrow factory interface.
- `open-request.js` owns Open request URL validation and session attribution for the `openUrl.publish` command. Intake, the `$BROWSER` handler, and delivery live in `../../open-url/` (see its `DOCUMENTATION.md`).
- `builtin-extensions.js` owns the list of Pi built-in extensions PiChamber loads (`codemode`, `tool-search`, `mcp`) and the list it skips on purpose (`llama.cpp`). Pi ships these inside the SDK package and only the Pi CLI loads them by itself, so the daemon passes them through `resourceLoaderOptions.extensionFactories` with the same `builtin: true` and `replaceable: true` flags the CLI uses. They load as `builtin:<name>`. `-builtin:<name>` in the Pi `extensions` setting disables one. Pi leaves one out when an installed extension registers the same tool, command, or flag, so a third-party MCP extension that registers `/mcp` takes over and Pi does not read `mcp.json`. MCP servers come from `mcp.json` in the agent directory and `.pi/mcp.json` in a trusted project. Each resident session runtime starts its own servers on `session_start` and stops them on `session_shutdown`, which every runtime disposal path emits. The MCP extension resolves `mcp.json`, `mcp-auth.json`, and `mcp.log` through the SDK's process-wide agent directory, so `daemon-process.js` sets `PI_CODING_AGENT_DIR` to the daemon's `--agent-dir` when one is given. Code that creates a daemon in-process with a custom `agentDir` must set that variable itself. `codemode` and `tool_search` are registered inactive. The MCP extension activates `codemode` for servers with the default `codemode` exposure and `tool_search` for `deferred` servers; `defaultTools` can activate them without MCP. Tool rows follow Pi's design: a `direct` MCP tool is an ordinary row rendered by its own `renderCall` and `renderResult`, `tool_search` is an ordinary row with the default display, and a `codemode` call is one row whose rendered result lists the nested calls with their status while the script runs. Nested calls stay out of the row list because their events carry `parentToolCallId`. The bridge reports `mode: 'tui'` by default (see `extension-ui-mode.js`), so `/mcp` opens Pi's interactive MCP manager through `ctx.ui.custom()` (see `extension-custom-host.js`), and `/mcp login <server>` signs in inside that manager; `/mcp logout <server>` and `/mcp reconnect <server>` act directly. The MCP extension is created with an `openUrl` that does nothing: Pi would open the authorization URL in a browser on the daemon host, which is often not the device in use and may have no display. The manager draws the URL as an OSC 8 hyperlink, which the browser renders as a link. PiChamber has no MCP settings screen.
- `extension-config.js` owns what `pi config`, `pi list`, and `pi remove` do for Pi extensions. Skills, prompts, and themes are not listed yet; the write functions already handle every resource type so adding them is additive. It uses the SDK's `DefaultPackageManager` and `SettingsManager` in-process and never runs the `pi` CLI. `list(target, replacements?)` takes the optional replacement facts from `extension-replacements.js` and adds `replaced`: `[{ kind: 'plugin' | 'builtin', id, registers?: { kind: 'tool' | 'command' | 'flag', name }, by?: { id?, name } }]`. A plugin entry's `id` is the PiChamber plugin id; a built-in entry's `id` is that built-in's item id in the same answer's `extensions` array (a built-in with no listed item is left out). `by.id` is the winning extension's item id when it is listed; otherwise `by` has only a path-free `name`. The field is present, possibly empty, only when a live runtime answered, and absent means unknown. Winner and built-in file paths are mapped to ids inside this module and never leave it.
  - Commands (private IPC): `extensions.config.list { directory? }`; `extensions.config.set { directory?, id, scope: 'global', enabled }` or `{ directory, id, scope: 'project', state: 'inherit' | 'load' | 'unload' }`, or `{ directory, id, scope: 'project', enabled }`, which the service turns into `inherit` when the project would get that value anyway and into `load` or `unload` otherwise, against the settings it reads under the lock (a client's copy of the global value can be stale); `extensions.packages.remove { directory?, id }`. Public routes: `GET /api/pi/extensions/config?directory=`, `PUT /api/pi/extensions/config/:id`, `DELETE /api/pi/extensions/packages/:id?directory=` in `../routes.js`, each with strict input checks and a whitelist projection.
  - Listing builds two views like `pi config`: a global view resolved with `projectTrusted: false`, and, when a directory is given and trusted, a project view. Trust follows Pi's `resolveProjectTrusted`: a saved decision wins; with none, a project with nothing that needs trust is trusted (`resolveDirectory` has already saved trust for a folder that has project resources), so in practice only a denied project is untrusted. Built-ins offered are `LOADED_BUILTIN_EXTENSIONS` (never `llama.cpp`). Listing never installs: it calls `resolve(() => 'skip')`, so a missing package shows `installed: false`. A package Pi could not resolve goes into `installFailures` and the rest still list. A project entry with `autoload: false` for a package the user also has is Pi's record of that project's overrides, not a second package, so it is left out of `packages` and its extensions stay under the user's package. An untrusted directory answers the global view with `project: { available: true, trusted: false }`.
  - No server path leaves the daemon. Ids are sha256 base64url over resource type, declaring scope, and the canonical path or `builtin:<name>` (packages: scope and Pi's package identity). An item the global view lists keeps the same id in the project view. Names follow `pi config`: the built-in name, `parent/file` when the parent folder is not `extensions`, else the file name. Package sources are npm and git sources as written with URL userinfo removed, and the folder name only for a local package. Error text is stripped of paths and credentials and capped at 300 characters.
  - Writes reimplement Pi's private toggle logic (`config-selector.js`) as pure functions over a settings manager: in global scope only user-scope items toggle (`+`/`-` entries, package filters in object form); in project scope each item takes `inherit`, `load`, or `unload`, inherited files are named by absolute path, built-ins by `builtin:<name>`, and a user package gets an `autoload: false` project entry that is removed again when it has no filter left. `BUILTIN_PATH_PREFIX` is a local constant pinned by a test. Recheck these functions on every SDK upgrade.
  - Every write re-resolves and rejects an unknown id (`RESOURCE_NOT_FOUND`), runs in the resource mutation queue under the shared Pi config lock, reads trust inside the lock (`PROJECT_UNTRUSTED` for project scope in an untrusted project, `INVALID_ARGUMENT` without a directory), and fails with `PI_SETTINGS_INVALID` when settings cannot be read or flushed. Removal calls only Pi's `removeAndPersist` (PiChamber deletes no path; local packages keep their files). A local package's source is passed as an absolute path, resolved against the folder its settings file is in, because `removeAndPersist` reads a relative source as typed in the daemon's working directory while settings keep it relative to the settings folder: `PACKAGE_REMOVE_FAILED` when npm or git fails, `PACKAGE_NOT_CONFIGURED` when settings had no entry, and `PI_SETTINGS_INVALID` when the files are gone but the settings write failed, which is never reported as success. After a write, resident runtimes are recreated through `scheduleRuntimeRecreation` (it recreates every resident runtime, for either scope); the answer is the fresh list plus `deferred: true` when a busy session delays that.
- `plugin-host.js` owns PiChamber plugins in the daemon (the server side is `../../plugins/`). The private, server-only `plugins.configure` command (`{ plugins: [{ id, entry, replaceable?, state: { global, projects, sessions? } }] }`, enabled plugins only) replaces the configured set. The host validates the payload (`INVALID_ARGUMENT`), imports each module only from under `packages/web/plugins/` (checked with realpath), and reports `{ plugins: [{ id, loaded, error? }], enabledChanged, deferred }`. One plugin that fails to import is left out and logged; the others still load. When the loaded set changes, the daemon calls `scheduleRuntimeRecreation()`, which is all or nothing: while any session in any folder is streaming, compacting, taking an input, or running a user shell command (`!cmd`), nothing is recreated and the answer is `deferred: true`; the change applies when that work ends, so a running turn or command is never cut. Recreation then disposes every resident runtime and recreates only the active one. The other sessions reopen from their files when next opened or prompted, and until then have no extension statuses, widgets, or composer controls; open drafts are discarded; a dialog or `custom()` surface left open is cancelled, as on a daemon restart. A composer control whose command the recreated runtime no longer registers answers `CONTROL_UNAVAILABLE` and never reaches the model as a prompt. A state-only change calls the `pichamber.onStateChange` listeners of live runtimes without recreation. Each loaded plugin becomes an `extensionFactories` entry after Pi's built-ins, in `createPiSessionRuntime` (through the `pluginExtensionFactories` runtime hook) and in `createFreshPromptServices`: `{ name: 'pichamber:<id>', replaceable, factory }`, listed by Pi as `<inline:pichamber:<id>>`. The factory calls the module's default export as `(pi, pichamber)` with `pichamber = { id, ui, state(directory, sessionId?), onStateChange(listener) -> unsubscribe }` (`ui` is the same `pichamber.ui` that `globalThis.pichamber` holds); `state` resolves `{ ...global, ...projects[directory], ...sessions[sessionId] }` (a session's own values are composer switches; up to 4096 sessions per plugin), and a runtime's listeners are dropped at its `session_shutdown`. The daemon never reads plugin state or the enabled set from disk, so a sandboxed daemon needs no grant for PiChamber's data folder. Until the server configures it, the daemon loads no plugins. The server pushes before the first request to each daemon process it has not configured (keyed by `streamEpoch`; see `../../plugins/DOCUMENTATION.md`). Each plugin factory runs for every runtime, also for a plugin Pi then drops as replaced, so the wrapper hands the factory a Proxy of Pi's extension API that notes the names passed to `registerTool`, `registerCommand`, and `registerFlag` (everything else forwards untouched). `registeredNames()` returns plugin id to `['tool:x', 'command:y', 'flag:z']` and `configuredIds()` lists the configured plugins; a plugin's names are forgotten when it leaves the configured set or its entry changes.
- `extension-replacements.js` finds what Pi left out of a live runtime. Pi drops a `replaceable` extension (PiChamber plugins and the `builtin:mcp`, `builtin:codemode`, and `builtin:tool-search` built-ins) when a non-replaceable one registers the same tool, command, or flag (`omitReplacedExtensions`), and keeps no record for plugins. A plugin counts as replaced when it is configured, its `<inline:pichamber:<id>>` path is not among the runtime's loaded extensions, and a loaded non-replaceable extension has one of the names the plugin registered (tools first, then commands, then flags); a missing plugin that shares no name is not reported, since it failed for another reason. A built-in counts as replaced when Pi's `warnings` hold an entry whose `path` is `builtin:<name>`; package and install warnings use other paths. Pi names the winner only inside that warning's text, so the optional `registers` and `by` details are parsed from it and left out when the text does not match. `extensions.config.list`, `extensions.config.set`, and `extensions.packages.remove` call it through `liveExtensionReplacements` in `session-daemon.js`, which never starts a runtime and never resolves a directory for it: it uses a non-draft runtime resident in the requested directory (the active directory when the request names none, and no other folder), and answers unknown (no `replaced`) when none is resident or when a runtime recreation is still queued, because that runtime predates the new configuration. Recheck the logic and the warning text against `omitReplacedExtensions` on every SDK upgrade.
- `extension-name.js` owns path-free extension display names for `extensions.list` and the `source` of runtime `extension.error` events. A single-file extension is named after its file; an `index` entry point is named after its nearest non-generic directory, or the package root for package extensions. Neither surface ever carries a server path.
- `extension-tool-render.js` owns daemon-side rendering for Pi extension tools that define `renderCall` or `renderResult`. Built-in tools are excluded so PiChamber retains native tool card rendering. Global Pi TUI theme symbols are installed once without overriding an existing theme. Partial updates render both the collapsed and expanded result slots (the browser draws the expanded slot only when a row is expanded), are throttled at 250ms with a trailing timer and component `invalidate()` trigger, the latest live render of a running tool is kept and included in session detail so a client opening mid-run sees the working state, settled results are rendered only for messages a history page selects (never for the whole branch) and memoized per toolResult message for history replay, and rendered ANSI lines are bounded to 100 columns, ≤200 lines, and ≤2000 characters per line. Its exported `renderComponentLines` helper carries those same bounds for message renders.
- PiChamber's own dialog calls live on `pichamber.ui`, not on Pi's `ctx.ui`, so a method Pi adds later cannot be shadowed by ours (`pichamber-ui.js`). `pichamber.ui.choose(ctx, title, choices, opts)`, `.form(ctx, title, fields, opts)` and `.openUrl(ctx, url)` each take the tool or handler `ctx` first; a missing or foreign `ctx` (no PiChamber session behind it) rejects with a `TypeError`, never throws synchronously. The working implementations hang on the session's ui context under a `Symbol.for('pichamber.ui')` key, which cannot collide with a name Pi adds and survives Pi's runner copying the ui context with an object spread; `pichamber.ui.x(ctx, ...)` reads them from `ctx.ui`, so no session lookup is needed. Plugins get the same `ui` on their handle (`plugin-host.js`); ordinary extensions get `globalThis.pichamber` (`{ version, ui }`, frozen), set next to the `__PICHAMBER__` marker, which stays as released. `ctx.ui.form` and `ctx.ui.openUrl`, released in 1.0.4 and 1.0.6, are removed, and `ctx.ui.choose` never existed: `ctx.ui` holds only what Pi defines. Plain Pi has no `pichamber`, so an extension checks for it and falls back to `select`.
- `pichamber.ui.choose` details: `choices` is `[{ id, label, description? }]`, at most 12, the first of each id kept; `opts` takes `message`, `allowNote`, `toolCallId`, and the usual `signal` and `timeout`. It resolves `{ id, note? }`, or `undefined` when the question is closed, times out, or is cancelled, and rejects with a `TypeError` when the title or every choice is missing (nothing is published, so the caller never waits on a question no client can see). The dialog event carries `method: 'choose'`, `choices`, `allowNote`, and `toolCallId`; a tool passes its own call id so a client can draw the question with that tool call (see the UI plugin documentation, Questions). `../extension-protocol.js` owns the limits, the projection (`projectExtensionChooseFields`) and the answer check (`validateExtensionChoiceAnswer`), shared with the public routes. A client that does not know `choose` shows the dialog with nothing to pick; it can only dismiss it.
- Partial tool results: the latest `tool_execution_update` result of each running tool is kept (`toolPartialBySession`) and returned on that tool's running part by `sessions.open` and `sessions.messages`, as `output` and `metadata`. A tool that reports once and then waits (Visuals' `render_choices` shows its options, then asks) is otherwise blank for a client that opens the session mid-call. Dropped when the tool ends, the run settles, the session closes, or the daemon stops.
- `extension-message-render.js` owns daemon-side rendering for `pi.registerMessageRenderer(customType, renderer)`. The renderer is resolved from the owning session's `extensionRunner` (a missing lookup function or a throwing lookup means no render) and called once collapsed (`expanded: false`) and once expanded (`expanded: true`) with `outputPad: 0`, `keyText()`/`keyHint()` from `extension-keybindings.js`, and the same extension theme tool renders use; each component renders at 100 columns through the shared line bounds, and every rendered line passes through attachment redaction. Live `extension.message` events and replayed `custom_message` history entries both carry optional `render: { message, messageExpanded? }` beside `customType`/`details` (public routes re-apply the same 200-line/2000-char caps and drop malformed shapes). Replay rebuilds the `{ role: 'custom', customType, content, display, details, timestamp }` input from the persisted entry so the renderer sees identical input live and on replay; renders resolve lazily for only the history page actually returned (the same pending-render mechanism as settled tool renders) and are memoized per entry. A missing/throwing renderer, a falsy component, or an empty collapsed slot omits `render` entirely; a failing or line-identical expanded slot omits `messageExpanded`. Renderer failure never breaks publication: the message still goes out with text/details, and other messages and sessions are unaffected. Only displayable messages (`display !== false`) render.
- `extension-palette.js` answers `extensions.palette`: what Pi's theme colour names (`accent`, `border`, `selectedBg`, ...) are for Pi-drawn lines in the browser (`ctx.ui.custom()` surfaces, tool and message renders, widgets, statuses), which carry them as marker-theme escapes. The browser sends the background, foreground and 16 colours it draws the surface screen with. With Pi's `theme` setting unset or `system`, the colours are Pi's system theme generated from that palette (`generateSystemThemeColors`); a named theme gives its own colours and export page background (as `#rrggbb`, converted from `#rgb` or `oklch()` with Pi's pi-tui), leaving out tokens it sets to `""` (terminal default) so the screen's own foreground and background apply; a `light/dark` pair picks by the palette's appearance; an unknown or invalid theme falls back to `system`, as Pi does. The setting is read from the global Pi settings only; a project's own setting is ignored so one folder cannot recolour another's surfaces. Settings that cannot be read fail with `PI_SETTINGS_INVALID` rather than answering with `system`, so the browser keeps PiChamber's colours. Pi exports none of this from its package root, so the module imports `dist/modes/interactive/theme/{theme,system-theme}.js` by path from Pi's install and checks the functions exist; if a Pi update moves them, the command fails, the browser keeps PiChamber's own tokens for Pi's names, and `extension-palette.test.js` (which runs against the installed Pi) fails. A failed load is retried on the next request. The route `/api/pi/extensions/palette` validates the input and whitelists the result.
- `extension-ui-mode.js` resolves the `ctx.mode` each extension binding reports from the "Extension interface" setting (`extensionUi` in `<dataDir>/pi/settings.json`, written by `../settings-store.js`): `terminal` or unset is `tui`, `dialogs` is `rpc`, so extensions that branch on the mode use Pi's standard dialogs. It changes only what extensions are told; `custom()` stays hosted in both. It is read once per binding (`createSessionDaemon({ resolveExtensionMode })` injects it, tests pin it), and Pi keeps a session's mode across reload, so a change applies to sessions started afterwards. A missing or unreadable file means `tui`; the settings page reports an invalid file when it loads. The `__PICHAMBER__` marker's `mode` is the value new sessions get; a session's own `ctx.mode` is authoritative.
- `extension-custom-host.js` owns `ctx.ui.custom()` surfaces: component lifetime, the TUI stub (`stop()`/`start()` throw), key focus, nested overlays from `tui.showOverlay`, overlay handles, render scheduling (the first change after a quiet spell draws on the next tick, later ones at most every 33 ms), and frames. Overlays are placed by pi-tui's own `resolveOverlayLayout` on a screen the size of the browser's chat pane (`screenColumns`); inline surfaces render at the composer column width (`columns`). Each session has one size, set by the client that last sent input, the Esc button, or a viewport report with `claim` (the driver; the browser claims on a tap on a surface or its dimmed pane). A new top-level surface goes to the client whose `clientId` came with the session's latest prompt, steer, follow-up, or `!command` (`openerClientFor`), at once if that client reported a size, else on its first report; a viewport report without `claim` never takes over otherwise, and a size change applies after 150 ms. Extension code never throws into a timer: an `overlayOptions` function that throws keeps its last options, any other render-time failure closes that surface, and a surface whose first render fails is removed before `custom()` rejects. A factory that resolves after its session closed or reloaded resolves `custom()` with `undefined` and shows nothing. Overlays a factory shows with `tui.showOverlay` before returning (Pi's overlay focus demo shows its panels from the constructor) become children of the surface once it opens, so ending it takes them along and keys sent to it reach the panel it focused; if the surface never opens they are removed, and `hideOverlay()` from a factory only touches its own overlays. `focus` (the browser's tab stack, `extensions.custom.focus`) does what `handle.focus()` does for a shown nested panel, makes the sender the driver, and redraws that panel's family, since extensions read `isFocused()` while rendering; it refuses top-level surfaces and hidden panels. The Esc button (`extensions.custom.close`, top-level surfaces and nested panels alike) presses Esc (`\x1b`) for the user through `handleInput`, once per press, because Pi has no host Close, `custom()` takes no cancel signal, and extensions that keep a handle to their overlay (pi-btw) only learn it closed from their own Esc handler. The Esc goes where a key typed at the surface would (an overlay it opened and focused, such as a confirmation, else the surface's component), even when the surface is non-capturing, unfocused, or hidden, and never reaches another surface or the session's turn. It does nothing a typed Esc would not: a component that closes itself ends with `done`, and one that stays open (an Esc that only stopped a running answer, a confirmation it opened, or a component that ignores Esc) stays open until the next press, as in Pi. Only a target with no `handleInput`, or whose Esc throws, is ended at once, so a surface that can never take a key cannot block the session: `custom()` resolves `undefined`, nested overlays go with it, and the dismissal is `cancelled`. `close` answers `{ closed: true }` once the Esc is delivered; the client keeps the surface until the dismissal arrives. Input requests are capped at 256 items and 65,536 characters in all (`isValidCustomInputItems`, checked by the route and here); keys stay with the surface they were sent to and its nested overlays, a non-capturing overlay takes keys only while it or an overlay it opened holds focus (as pi-tui hands keys to the focused component), and keys for an open surface that takes none right now are dropped with an accepted reply, not a not-open one. SGR mouse reports (`\x1b[<b;x;y(M|m)`, cells local to the surface) never reach `handleInput`: they become pi-tui `TuiMouseEvent`s routed as pi-tui's alt screen does (`dispatchMouseEvent`; the press target keeps the gesture, a release on the press cell adds a `click` with a 500 ms click count, `capture`, `focus` and render defaults follow pi-tui). Mouse reports also reach non-capturing overlays, and a `focus` answer gives one the keys; since PiChamber sends no extension shortcuts, a press on a non-capturing overlay whose component has `handleInput` also gives it focus. Frame lines are capped at `MAX_CUSTOM_LINE_CHARS` (16,384) by `capLine`, which never cuts inside an escape sequence or a surrogate pair. Every surface ends exactly once (`done`, the Esc button on a surface that takes no keys, render error, session close, reload, daemon stop) with a resolved promise, a disposed component, and an `extension.custom.dismiss`. Capturing top-level surfaces register with `pendingInput`, and an open surface blocks idle disposal. `extension.custom` metadata and dismissals are ordinary replayed events; `extension.custom.frame` is published with `publishTransient`, which shares the sequence and stream epoch but skips the replay log, so a subscriber that attached by replay is sent each open surface's full frame afterwards (`keyframes`), and snapshots and `sessions.open` detail carry `extensionSurfaces` with full frames. The bridge's `custom()` delegates here; the bridge reports `mode: 'tui'` by default, so extensions that check `ctx.mode === 'tui'` (Pi's `snake`, `todo`, `question` examples, the MCP manager) open surfaces. `setHeader`, `setFooter`, `setEditorComponent` and `onTerminalInput` stay no-ops.
- `extension-controls.js` owns composer controls that plain Pi extensions declare by emitting `pichamber:composer` on `pi.events` (`toggle`, `cycle`, or `action`, each naming the extension's own commands; `{ id, remove: true }` takes one away). `createComposerControlsExtension` is a hidden inline factory (`<inline:pichamber:composer-controls>`, filtered out of `extensions.list`) that every runtime loads after the user's extensions; it holds emits until `session_start` names the session. `parseComposerControl` validates and cleans each payload (invalid ones are ignored like a malformed status); `createComposerControls` keeps up to 16 per session, publishes `extension.control` (`{ control }` or `{ id, removed: true }`), and resolves a click to a command, or to none when the requested value is already current. The private `extensions.control` command (`{ sessionId, id, value?, clientId? }`) checks the command is registered (`CONTROL_UNAVAILABLE` otherwise), then runs `/<command>` through `runSessionInput` as a typed extension command (steering delivery while a turn streams, so it runs at once), leaving the draft mirror alone; it answers `{ ran }` and the new value arrives as the extension's next emit. Snapshots and `sessions.open` always carry `extensionControls` as a list (empty is authoritative); session reload clears them with a removal per control and extensions declare them again at `session_start`.
- Draft sessions (`session-daemon.js`, `draftSessionIds`): `sessions.create` with `draft: true` (no title, parent, or `draftSessionId`) starts a session for a new-session draft before anything is sent, so its extensions can declare composer controls and run their commands. The `beforeSession` runtime hook marks its id before Pi starts it, so everything it publishes, from `session_start` on, carries a top-level `draft: true`; a draft is never the active session (`activateSession` returns its runtime without switching, so `dormantSession` never names it), never a target for unattributed Open requests, and stays out of `sessions.list` and `sessions.pendingInput`. It gets the five-minute idle lifetime at once, so an abandoned draft is disposed and reported deleted (still marked). A draft is never the general runtime `ensureRuntime` hands out for a folder (catalogs, recreation), never a target for any Open request (named or not). A model turn ends a draft: when one starts on a session still marked (a control's command calling `sendUserMessage`), Pi has already written the session file, so at `agent_start` the daemon publishes one last marked `session.lifecycle` (`state: 'busy'` without `command`, which a command-only run always carries), removes the mark, and publishes the same state unmarked. From then on it is an ordinary listed session; the drafting client lets go of it on that marked event, `sessions.discardDraft` answers `{ discarded: false }`, and a later `draftSessionId` create falls back to an ordinary create. Disposal of a draft is forceful: idle disposal and `sessions.discardDraft` cancel its dialogs, close its `custom()` surfaces, abort anything running, and wait (bounded) for a control's command to settle, so a draft waiting on a dialog nobody can see cannot live forever; ordinary sessions keep every idle guard. When every runtime is disposed (`disposeRuntime`: runtime recreation, daemon stop), each draft gets a `session.deleted` still carrying `draft: true` before its mark is dropped (on stop, clients are already gone). Create paths that fail dispose a draft before unmarking it, so what disposal publishes stays marked. `sessions.create` with `draftSessionId` adopts it when it is still a draft in the same folder and no parent is asked for: its idle timer is cleared first, adoption waits (up to 5 s) for a composer-control command still running in it, then the mark is cleared, model and thinking are set only when they differ (on failure it is marked again and its idle timer re-armed), the title is appended, and it becomes the active session with the same id and whatever its controls did. Otherwise a stale draft is discarded and the session is created as usual. `sessions.discardDraft` (`{ sessionId }` → `{ discarded }`) disposes a draft whose draft closed; it acts on drafts only and is deliberately outside the session-access guard, which would make the disposal it asks for unsafe. The server routes it as `POST /api/pi/sessions/:id/discard-draft`, passes `draft` through `projectEventFrame`, and the notification watcher ignores marked events.
- `extension-keybindings.js` owns the `KeybindingHints` (`keyText()`, `keyHint()`) that Pi 1.5.0 passes to tool renderers and message renderers. Pi's keybindings are terminal shortcuts, and PiChamber binds none of them: rows expand on click. So `keyText()` returns an empty string and `keyHint()` returns only the description, styled `muted` as in Pi, with no leading space. A Pi hint such as `(40 more lines, ctrl+o to expand)` reads `(40 more lines, to expand)`. Neither function throws.
- `session-daemon.js`
  - `createPiSessionRuntime({ cwd, agentDir })` creates a persistent Pi runtime using the selected server-side cwd and Pi agent directory. It uses Pi's normal settings, credentials, models, sessions, skills, prompts, context discovery, and native extensions. The archive file is written first through `archive-store.js` `archiveMissing`; if that write fails, the migration retries on the next read or write. Until it succeeds, reads return the snooze-only view and snooze writes still go through, with every unmigrated settled mark written back unchanged. A send (`clearForActivity`) or a delete (`remove`) also drops that session's settled mark, so the retried migration never archives a session the user just used. Older clients that still send `settled: 'settled'` archive the session; `'active'` and `null` are no-ops. The older-client mapping is removed one release later.

- Archive changes reach every device: after the archive route, the older-client `settled: 'settled'` shelf write, or an unarchive on send saves the mark, `routes.js` asks the daemon to publish it (`archive.publish`, private, server-only, `{ sessionId, archived, directory? }`; without a directory the daemon uses the resident session's cwd). The daemon publishes `session.archive` (`{ archived }`) on that session's stream, which every subscriber receives. It is a signal, not state: a client whose catalog row disagrees re-lists that folder (coalesced per folder), and the archive store stays the authority. The request is fire-and-forget; a failure (such as an older daemon) only logs, and devices catch up on their next list.

- Daemon routing in `../routes.js` (`registerPiRuntimeRoutes({ daemonPool })`; without a pool it wraps `getPiSessionDaemonRuntime` as the main daemon). Session- and directory-scoped commands (session actions, `sessions.create` by `cwd`, `sessions.list`, `sessions.rename`, `sessions.sendReceipt`, `resources.list`, `extensions.list/respond`, the archive and shelf membership lists, `archive.publish`) go to `forDirectory(directory)`; the daemon payload is unchanged. The client's folder applies only to a session not yet written to disk. Every response that carries a project daemon's state is tagged with that daemon's `stream` id: session detail, create, navigate, fork and clone, messages, and the list. Clients check such a response's `streamEpoch` against that stream, not the main one. `sessions.pendingInput` fans out to every live daemon. The top-level `sequence` and `streamEpoch` are the main daemon's, and its entries carry no `stream`. A project daemon's entries carry its `stream`, and its position is under `streams[stream] = { sequence, streamEpoch }`. A failed or malformed daemon is skipped and the response gains `incomplete: true` (clients then set the listed entries but clear no absent row). If the main daemon failed, the top-level `sequence` and `streamEpoch` are absent. Only when every daemon fails does the route fail. `sessions.list` for a folder is the owner's list. Each draining daemon's list for the same folder only fills in `live` and `inputState` on owner rows that lack them, matched by session id. Such a row also gets that daemon's `stream` (`main` for the main daemon) and `streamEpoch`, so clients order it in that daemon's sequence space. A failed draining daemon leaves those rows unknown. A failed owner fails the list. The all-sessions list (no folder) is the main daemon's, with `live` and `inputState` filled the same way from every live project daemon's list.
- `../merged-event-stream.js` (`subscribeMergedPiEvents`) is the `/api/pi/events` subscription across the pool. The main daemon is subscribed exactly as before: same options, unchanged frames, its resume position still `fromSequence` + `streamEpoch`. Its failure still ends the connection. Each project daemon is subscribed alongside it. Its frames gain `stream` (its public id) and `cursor`. The cursor is opaque base64url JSON (`{ v: 1, d: { [stream]: [epoch, sequence] } }`) covering every project daemon, never the main one. A client sends its newest accepted cursor back as `?cursor=`. Each project daemon then resumes from its entry, and a daemon whose lifetime changed answers with a resync snapshot. `decodePiEventCursor` bounds the cursor (4096 characters, 64 streams), and a malformed one is a 400. A cursor sent to a daemon without `events.streamEpoch` is a protocol mismatch. Only the affected daemon's sessions resync. A daemon registered mid-stream is subscribed without a position (snapshot baseline). A replaced runtime (restart) is resubscribed from its old position, so the new process resyncs. A removed daemon is unsubscribed and dropped from the cursor. A project daemon whose subscription fails is dropped and retried alone with backoff (500 ms doubling to 30 s) while it stays registered, without ending the connection. Each connection remembers which daemon last delivered each session (bounded to 4096 sessions). A frame for a session from a different daemon, a daemon detaching, or `pool.announceMove` emits a server-made `session.moved` frame (`sequence: 0`, no `streamEpoch` or `stream`) before anything from the new owner. Clients drop that session's live state and refetch it.
- `../event-stream.js` owns the `/api/pi/events` SSE connection lifecycle so `../routes.js` stays a thin adapter. Per connection it installs cleanup before `subscribe` is awaited (a client that leaves during the opening window cannot leak a daemon subscription; a late subscription is closed exactly once), funnels client disconnect, subscription error, and server shutdown through one idempotent cleanup, hands an `AbortSignal` through the supervisor to the private IPC subscriber, never writes a named heartbeat or a late frame to a dead response, and byte-bounds the response socket buffer (`res.writableLength`, default 8 MiB, aligned with the daemon replay budget) with the bound enforced BEFORE each write so no single frame overshoots it. A client that stops reading is disconnected recoverably — the stream ends and the client reconnects from its last accepted sequence for replay or an authoritative snapshot, so no event is silently removed from an otherwise contiguous stream, but frames still buffered when the disconnect fires are not promised as delivered; the reconnect replay is the delivery guarantee — while a healthy client's connection stays independent of the slow one. Every teardown is bounded: a `write()` that returns false starts a drain deadline (default 5s) that ends even a quiet never-draining client, and after `res.end()` a terminate deadline (default 5s) destroys the response, because `end()` alone only queues the FIN behind unflushed data and would otherwise leave a stalled socket open forever and hang server shutdown/close. The response `'error'` guard stays attached for the response's lifetime (idempotent; cleanup can complete while data is still in flight and a late unhandled `'error'` would crash the process). The registry tracks live connections so `registerPiRuntimeRoutes` can expose `closeEventStreams()` for server shutdown, ending active and still-opening streams (and their daemon subscriptions) before the HTTP server closes. The IPC subscriber removes its abort listener and destroys the opening or active daemon socket on cancellation.
- `*.test.js` uses temporary cwd, agent, data, and runtime directories; it never loads a developer's Pi home, credentials, or sessions. On Windows the private endpoint is a named pipe, not a `.sock` file, and POSIX mode-bit assertions are skipped.

## Protocol and security invariants

- Each profile owns its daemon artifacts: `<dataDir>/pi/daemons/<profileKey>/` holds the credential, `daemon-state.json`, and `operation.lock` (a sandbox daemon's lock, launcher record and credential are in `<dataDir>/pi/launchers/<profileKey>/` instead; see "Sandbox launchers"); the endpoint is `<runtimeDir>/pi-daemons/<profileKey>/daemon.sock` (or `$XDG_RUNTIME_DIR` equivalent); per-profile logs append to `<dataDir>/logs/pi-daemon-<profileKey>.log`. The state sidecar records `profileKey`, `serverInstanceId`, `serverPid`, `daemonId`, `runtime`, and `buildId` alongside pid, endpoint, and entrypoint. A pre-profile legacy daemon is never adopted, unlinked, or signaled; only its dead pid record is best-effort removed.
- The endpoint is a Unix domain socket on POSIX or a Windows named pipe. TCP endpoints are rejected. Listeners and clients connect with IPC `path` options so Windows `\\.\pipe\pichamber-pi-session-daemon-<owner-key>-<profileKey>` works the same as a POSIX socket path. `PICHAMBER_PI_SESSION_DAEMON_ENDPOINT` still overrides the socket path, but the credential, state, and lock stay per-profile: a profile never adopts, unlinks, or signals an endpoint it cannot authenticate and identify as its own, and the conflict surfaces as `DAEMON_ENDPOINT_UNVERIFIED`.
- POSIX socket parent directories are mode `0700`; the socket is created mode `0600`. An existing endpoint fails startup rather than being unlinked without daemon-identity verification. Windows named-pipe ACLs are not yet equivalent owner-only OS permissions; credential authentication remains mandatory.
- The daemon credential and non-secret state sidecars are mode `0600`; their per-profile parent directory and the operation lock serialize start/reuse/stop. Exclusive lock create writes the owner pid in the same step. A leftover empty or malformed lock, a dead owner pid, or Windows `EPERM`/`EACCES` on exclusive create is retried and stolen after a short freshness window instead of failing as `DAEMON_LOCK_UNAVAILABLE`. Sidecar `chmod` failures on Windows are ignored after the file exists so readiness is still recorded. Health identity includes the daemon PID, profile key, and daemon id, and all three must match the state sidecar before the supervisor reuses a process. Reuse also requires the ready-state `entrypoint` to equal this host's `daemon-process.js`; a missing or different path is not identity-compatible and is replaced after a claim.
- Ownership transfers through authenticated `runtime.claim` only after the previous server PID is no longer live. The daemon persists the new `serverInstanceId` and `serverPid` to its state sidecar before acknowledging the claim, so its in-memory owner and discoverable owner cannot split. Shutdown goes through authenticated `runtime.shutdown` (profile, daemon id, and current owner instance must all match) before any signal; a stale server whose daemon was claimed receives `DAEMON_OWNERSHIP_MISMATCH` and terminates nothing. A direct signal is used only after authenticated health and ownership checks prove that the sidecar PID is this profile's daemon (or for a child the supervisor just spawned during failed startup).
- Shared writable state is coordinated, not merely namespaced. Pi prompt, context, settings, and model writes serialize through `<agentDir>/.pichamber/locks/pi-config.lock`; `models.json` additionally serializes in its store. PiChamber data-root stores (`pi/settings.json`, `pi/snippets.json`, `pi/session-archive.json`, `pi/session-folders.json`, root `settings.json` and `runtime-state.json`, STT config, remote-client and pairing stores) serialize read-modify-write through per-file locks with atomic replace; `session-folders.json` additionally rejects a stale `updatedAt` snapshot as `SESSION_FOLDERS_STALE` (HTTP 409) instead of silently overwriting newer folders. Passkeys, the JWT secret (exclusive create with re-read), the tunnel token, and git identities use atomic replace. Cross-daemon config staleness is bounded by idle runtime disposal (five minutes), which recreates runtimes from disk; there is no cross-daemon live-reload generation yet.
- The public health route deliberately whitelists its response fields (state, protocol version, capability names, and the opaque public `streamEpoch`). It never returns a daemon endpoint, credential, PID, cwd, agent directory, or transcript data. Public transcript and event projections preserve daemon-redacted assistant error messages so the UI can distinguish provider/runtime failures instead of reducing every failure to `ASSISTANT_ERROR`.
- A client must send an `authenticate` frame carrying the host-private daemon credential before it can issue a request. Credentials are never logged or returned.
- Frames are LF-delimited JSON. One frame has a 16 MiB maximum. Complete frames are parsed before the client bounds the remaining incomplete frame. Invalid JSON reports `MALFORMED_DAEMON_RESPONSE`; an oversized response reports `DAEMON_RESPONSE_TOO_LARGE`. A malformed, oversized, unauthenticated, or invalid request closes the connection.
- The private core commands are `runtime.health` (its result includes `residentSessions`, the count of live and starting runtimes, which the sandbox manager reads for idle stop), `projects.list/select`, `providers.list/hosts/config.get/models.set/models.add/status/login/login.respond/login.status/logout` (`providers.hosts` returns the sorted, lowercase hosts of signed-in providers' model base URLs, skipping loopback and IP literals, for sandbox network grants; Pi agent-core emits streaming assistant starts as shallow copies, not as the finalized object it later persists. Alias keys include cwd and session ID, survive idle runtime disposal of persisted sessions, and clear on explicit session deletion, confirmed ephemeral expiration (which publishes `session.deleted`), or daemon shutdown. Hydrated message projections continue to use the Pi entry ID directly.
- Each event and reconnect snapshot has a monotonic sequence. Replay is capability-negotiated: the subscriber stamps its cursor with the `streamEpoch` it was established under, a marker-less cursor fails as `DAEMON_PROTOCOL_MISMATCH`, and a cursor from a retired epoch resyncs from a snapshot instead of replaying — even when this daemon's sequence numerically overtook the old cursor, replaying from it would silently skip the head of the new space. Every event, snapshot, and health result carries an opaque random `streamEpoch` regenerated on every daemon process start (never derived from daemon id, profile key, pid, or any private identity); `runtime.health` advertises the `events.streamEpoch` capability, session reads stamp it so clients can reject stale-epoch responses, and a snapshot published because the cursor could not be replayed is additionally stamped `resync: true` as a recovery baseline. A reconnect replays the retained contiguous suffix after its cursor when available, otherwise it receives an authoritative `session.snapshot`; unavailable runtimes are not represented as empty sessions. The suffix lives in `session-replay.js` and is bounded by both count (1,024 events) and encoded wire bytes (8 MiB): eviction removes whole oldest events first and never truncates content, each event is serialized once and the cached line is reused for live broadcast and replay, and live delivery stays full-fidelity even for events too large to retain. The byte budget counts encoded wire bytes, not heap, and snapshots assign sequence numbers without replay insertion so numeric gaps from private snapshots are intentional. A single oversized event clears the retained suffix without being retained, an empty ring never replays, and a cursor beyond the latest sequence resynchronizes from a snapshot; contiguity is judged on the global suffix while delivery stays session-filtered, so a filtered client never replays through a gap. A missed suffix recovers through `session.snapshot` plus `sessions.open` hydrate, which re-reads persisted entries for tool finals and lifecycle.
- Prompt, steer, and follow-up requests acknowledge acceptance only after the Pi SDK preflight signal (`session.prompt` with `preflightResult(disposition)` where `disposition` is `'started'`, `'queued'`, or `'handled'`); the daemon owns the still-running turn promise and publishes any asynchronous rejection as `session.error`. A preflight rejection (`session.prompt` promise rejecting without calling `preflightResult`) propagates as the request rejection so dedup never caches it as accepted and the operation id stays reusable. Plain text uses prompt() with expandPromptTemplates:false and source:extension plus images; slash input keeps source:rpc. Pi can emit the live user-message start before that message is branch-readable, so the daemon queues each accepted prompt's path-free file metadata per delivery kind (`prompt`/`steer`/`followUp`) and adds it to the matching user start. SDK `queue_update` shrink is the authoritative owner of the next user start (steering drains before followUp regardless of send order); direct starts emit no shrink and fall back to oldest-by-generation. Requested `steer`/`followUp` always travels as SDK `streamingBehavior` (ignored while idle) so an idle arrival that races another sender still queues. Retention is decided at resolution from the SDK preflight disposition: `'queued'` keeps the metadata, `'handled'` and registered extension commands never do, and `'started'` keeps it only while the session is still streaming; only queued resolutions keep metadata until their per-delivery start, all other completions clean a still-pending entry (an extension command that never emits a user start). The browser can render the attachment footer immediately without exposing bytes or server paths, while later hydration remains authoritative. An extension command may resolve without starting an agent turn, so completion of its non-streaming prompt promise publishes the idle lifecycle boundary that Pi does not emit as `agent_settled`. Pi notifies extensions of model switches (`model_select`) but not session subscribers, so that same completion edge also reconciles a changed live model into `session.model` before the idle boundary; thinking already emits `thinking_level_changed` to subscribers and needs no reconciliation. A registered extension invocation is not used for automatic first-prompt naming: an extension-only empty session remains unnamed unless the extension names it, and the first later conversation prompt supplies the derived title. Classification uses the active Pi runtime's registered extension commands, not a browser claim. Manual compact requests likewise acknowledge startup instead of holding the public/private request open for the summarization call; the daemon-owned promise reports its outcome through `session.compaction`. A second compact request while Pi is compacting fails as `SESSION_BUSY`, and optional `/compact` instructions pass to `AgentSession.compact(customInstructions)`. A later prompt on the same session invalidates an older send rejection so it cannot error the new turn. If the rejected send left Pi streaming, the daemon aborts it. Steer/follow-up against an idle session starts a new prompt instead of `SESSION_NOT_RUNNING`. A registered extension command running without an agent turn (waiting on `custom()`, a dialog, or its own work) keeps the session busy, as Pi's interactive mode holds input until the command returns: the daemon publishes `session.lifecycle: busy` with `command: '/name'` when it dispatches, snapshots, `getSession`, and list live status report the same, and prompt, steer, and follow-up fail as `SESSION_BUSY` until it returns, because the SDK would start a second run beside the command (steering only queues behind a streaming turn). While the command's own agent turn streams, input behaves normally; when that turn settles and the command still runs, the busy frame with `command` is published again instead of idle, and the settled turn neither completes a requested shutdown nor re-arms idle disposal. A command that returns or throws publishes idle from its own settlement, whatever the send generation (a steer into the command's turn moves it on), unless a turn still streams, whose `agent_settled` then publishes idle. `!cmd` (`sessions.bash`) and `sessions.compact` are refused the same way. The busy check runs again after the model and attachment awaits, so two clients cannot both start beside a command. Command detection follows Pi's `_tryExecuteExtensionCommand`: the text (with appended attachment notes) must start with `/`, and the name up to the first space must match a registered `invocationName` exactly. Agent and compaction completion are never held behind the 30-second public/private request budgets. Pi retryable provider failures remain live: an `agent_end` with `willRetry` does not publish terminal `session.error`, and `auto_retry_start` projects Pi's attempt, next-attempt time, and redacted error text through `session.lifecycle: retry`. Retry metadata is retained in reconnect and `getSession` snapshots until the next `agent_start` begins the attempt. `agent_settled` remains the authoritative idle boundary after retry success, exhaustion, or cancellation and clears the run's user/assistant ownership.
- Send-intent deduplication (`send-operation-registry.js`) owns the authoritative execution boundary for prompt/steer/followUp: the client labels each intent with a stable `operationId` and the health-verified `streamEpoch`, the daemon claims `kind + sessionId + operationId + streamEpoch` BEFORE Pi activation, and an identical same-epoch retry returns the original acceptance receipt (`{ accepted, messageId, deduplicated: true }`) without invoking Pi again. A concurrent duplicate of a still-pending intent shares the original outcome; the same full key with a different payload (text, model, thinking, message id, or attachments) fails as `OPERATION_PAYLOAD_MISMATCH` (HTTP 409). An intent from another daemon lifetime fails as `STALE_STREAM_EPOCH` (HTTP 409) before Pi or attachment-consumption side effects. The same id on a different kind or session is a different intent and executes independently, never a mismatch. Only acceptances are retained: request-path rejections happen before Pi runs (nothing executed, id reusable) while pending duplicates still share the original rejection, and every claim settles so pending duplicates never hang. Retention is bounded: receipts expire after `sendOperationTtlMs` (default ten minutes) and at most 1,024 accepted receipts are retained (oldest evicted to a bounded expired tombstone); pending claims are bounded separately (256 entries, never expired while active, new distinct pending past the bound fails as `SESSION_BUSY`). An expired or evicted id reports `expired` and a retry with the same id fails as `OPERATION_EXPIRED` (HTTP 410), never an automatic re-execution — callers must use a new operation id. `sessions.sendReceipt` is the exact read-only receipt lookup for an uncertain send: it requires the full `kind + sessionId + operationId + streamEpoch` identity; a missing epoch returns `unknown`, never invokes Pi, and returns `accepted` (retained receipt), `pending`, `expired` (seen but retention gone, outcome unknown, never assume success), or `unknown` (never seen in this retention window, tombstone pressure, post-restart, or rejected before Pi ran). The registry is in-memory per daemon process with bounded tombstones (`expired` degrades to `unknown` under pressure): there is no lifetime receipt guarantee, only within the retention window. A restart loses receipts, but the replacement daemon rejects the retired epoch instead of replaying the old intent. Receipt lookup and replay protection remain separate read-only contracts.
- Registry keys combine the SDK session ID with its cwd. A replacement subscription is rebound to the replacement session so old-session events cannot be published under the new identity. A collision is a visible error; it never replaces or disposes an unrelated runtime.
- A command that names a directory (`extensions.list`, `resources.list`, `providers.list`) is answered only by a runtime resident in that directory. `ensureRuntime` resolves the request through the runtime registry (`listByDirectory`), prefers the active runtime when it already serves that directory, otherwise uses a runtime already resident there, and starts one owned by it when none is; a concurrent start is shared per directory, never across directories. Answering for a directory that is not the daemon's active one stays non-active, including after idle disposal has cleared the active runtime (only a start in the active directory is adopted): it never replaces the active runtime or active directory, never replaces the remembered dormant session, reopens no dormant JSONL owned by another directory, and arms the same idle lifetime as any other view-only session, so browsing many projects cannot accumulate resident runtimes. A directory-less command keeps answering for the daemon's active directory. One project's loaded extensions, skills, prompts, and models are therefore never reported for another project.
- After `agent_settled` or a terminal compaction that will not resume the turn, the daemon disposes an idle runtime after five minutes (injectable for tests). View-only access (`sessions.open`, `sessions.messages`, `sessions.tree`, plus navigate/fork/clone/abort/model/thinking/rename settlement) arms the same lifetime through `touchIdleDisposal`, so browsing old sessions without prompting cannot grow the registry unboundedly while the UI keeps only a bounded transcript cache. Disposal never deletes Pi JSONL; when the assigned session file exists on disk, the daemon remembers the selected session file and recreates that runtime on the next private prompt or open. When the assigned JSONL is positively absent (stat reports ENOENT only, determined after dispose while the resident lease is still held and before any release), the session is ephemeral: after a successful lease release the disposal clears matching dormant state plus the same safe per-session auxiliary state as explicit deletion where applicable (messageEntryAliases for cwd/session, retry/compaction/run-start/shutdown) and publishes the existing `session.deleted` event so connected clients remove it. Publication happens only after a successful release, which closes the cross-daemon recreate race. Runtime recreation after a provider, trust, or resource change (`disposeRuntime`) first records the session the active runtime holds at that moment (navigate or fork may have moved it since activation), then applies the same rule to that dormant session before reopening it: when its JSONL is positively absent, the dormant entry is dropped so the next `ensureRuntime` starts a fresh session instead of failing every later read as `SESSION_JSONL_UNREADABLE` (issue #252). This covers the implicit catalog session a fresh install starts before any message, which held no lease and is dropped silently, and an unsent `sessions.create` session, which is announced with `session.deleted` after a successful lease release. A missing/throwing getSessionFile or a non-ENOENT stat failure cannot prove absence and never claims deletion, a failed disposal retains ownership (registry entry, lease, and global runtime) without emitting deletion, and persisted sessions keep dormant state for reopen. The touch clears first and re-arms only when the session is resident and idle-safe, so a read cannot race a pending operation and a repeated open extends the deadline. Agent and compaction starts cancel pending disposal, and prompt/compact entry clears it before activation. The timer refuses to dispose a session while `isStreaming` or `isCompacting` is authoritative, while a send is in flight (`activeSessionInputs`), while a resource reload is pending or running, while a provider retry is scheduled, while compaction is running/retrying, or while a hosted input request is pending in the pending-input index; a dialog opened while the session is idle (for example from a command or event handler) therefore survives the five-minute timer so a user who walks away finds it still pending later. When the last hosted request settles, the index re-arms the idle timer through the disposal touch, and disposal proceeds as usual. Deletion and daemon stop still cancel dialogs with an authoritative dismiss event. A read or prompt that arrives during an in-flight disposal waits for it and reopens from JSONL instead of adopting a dying runtime. There is deliberately no acquisition-path eviction: capacity pressure alone never disposes entries that are actively mounting.
- Ephemeral sessions: Pi's `SessionManager` defers JSONL creation until the entries contain a user or assistant message, so `sessions.create` alone stays ephemeral (untouched sessions vanish on restart by design). A rejected first prompt likewise persists nothing: the runtime stays resident and retryable until normal idle disposal, which reports the session as deleted when its assigned JSONL is positively absent (see above). Failed `sessions.create` cancellation and lease-acquire failures dispose without persisting and release (or never hold) the lease. Model/thinking setup failures after lease acquisition dispose first and release only after successful disposal: a disposal rejection retains `{ runtime, cwd, sessionId }` in daemon-owned pending failed-create state without releasing ownership, registering the runtime, or installing dormant state, while still throwing the original model/thinking error; `sessions.delete` retries its session entry and daemon stop retries all entries (dispose-first, release-after-success, failed retries stay pending without releasing ownership, entries removed only when still current, disposal exactly once).
- A startup validation failure writes only a stable failure code to the owner-only non-secret state sidecar. It never records a transcript, session path, or credential. The supervisor surfaces that code as unavailable instead of claiming an empty or idle session.
- After a forced crash, the next health, request, or subscription probe re-runs supervised startup. Each private health probe uses the supervisor's five-second operation budget; it must not inherit the general 30-second command timeout and hold every browser request until the browser aborts. Daemon readiness has its own 15-second bounded budget, separate from the shorter probe, lock, and shutdown budget, because loading Pi settings and provider/model catalogs can legitimately exceed five seconds. The supervisor removes an existing POSIX socket only when its recorded daemon PID is dead, the endpoint is a socket, and authenticated IPC deterministically refuses or times out. An endpoint that responds, authenticates incorrectly, returns malformed protocol data, or cannot be classified remains `DAEMON_ENDPOINT_UNVERIFIED`.
- The web server creates its supervisor after HTTP listen so the profile key uses the bound port, then warms it without awaiting Pi provider/model initialization. A first request arriving during that warmup shares the supervisor's `startPromise`. The bound profile key travels back over the `pichamber:ready` IPC message and into the CLI instance file; `pichamber logs` uses that key to include the matching private daemon log, while `--json` and `--quiet` serve output still carries only the port.
- The daemon owns the runtime after clients disconnect. Disconnecting the web-server client cannot stop active Pi work.

## Session engines

The daemon accepts an `engines` array of engine factories (`(host) => engine | Promise<engine>`, validated synchronously as `INVALID_ENGINES` when not an array of functions). `engines/index.js` is the single registration point and ships empty, so with no engines every routing branch is guarded by "registry has engines" or "an engine owns this session" and the zero-engine path runs exactly the Pi-only code: same responses, events, and frames.

An engine implements `id` (lowercase alphanumeric/hyphen, never `'pi'`), optional `label` (non-empty, at most 64 characters, defaulting to the id), sync `ownsSession(sessionId, directory?)` / `ownsProvider(providerId)` answered from its own index, async `listSessions(directory, { signal })` / optional `listProviders({ signal })` in Pi row/provider shape that must throw on failure, a `handlers` map for session-scoped commands, sync `snapshot(sessionId)` that must include an absolute `directory` (otherwise it is treated as unavailable), and async `dispose()`. Handler keys must belong to the routed session commands plus `sessions.create`; an unknown key, a non-function value, or a missing `handlers` object is `INVALID_ENGINE`, as are a bad id/label or shape. Detail handlers (open/messages/navigate/fork/clone/create) return a Pi-shaped detail; prompt/steer/followUp return `{ messageId }`; anything else returns a result object or undefined. A routed command with no handler fails as `ENGINE_UNSUPPORTED_OPERATION` (HTTP 409) automatically; engines never write it themselves. `commands` in `engines.list` is the sorted handler keys. Engines own their own event publication (`session.deleted` after delete, `session.updated` after rename) through the host `publish(event, payload, sessionId, directory)` wrapper, which requires an absolute `directory` (never falling back to Pi's active project), redacts attachment paths, rejects `session.snapshot`, missing ids, and a missing/relative directory as `INVALID_ARGUMENT`, strips spoofable `sessionId`/`directory` payload keys, and otherwise shares the global sequence, stream epoch, and replay log, so engine events are indistinguishable on the wire and replay to reconnecting subscribers. The host also exposes `prepareAttachments(attachments)`, the same preparation Pi prompts use: it returns `{ text, images, files }` where `text`/`images` carry server-local paths and file bytes for the native agent only (never for published events or results; redaction remains as a backstop) and `files` is path-free metadata. An engine publishing its own live user start publishes `assistant.message.start` with `role: 'user'` and includes that `files` metadata as path-free `file` parts (`{ type: 'file', id: `${messageId}:file:${index}`, index, mime, filename }`), the same shape Pi uses, so the browser shows the attachment footer immediately.

Routing is ownership-first: a command in the engine command set (open/messages/rename/delete/tree/navigate/fork/clone/prompt/steer/followUp/abort/setModel/setThinking/compact) with an explicit `sessionId` dispatches to the first owning engine in registration order and skips the Pi idle guard entirely; unowned sessions fall through unchanged, and Pi's default-to-active-session fallback never selects an engine. `extensions.draft` on an engine-owned session fails as `ENGINE_UNSUPPORTED_OPERATION` without touching Pi. Draft sessions are Pi-native: a `sessions.create` with `draft: true` or `draftSessionId` that would route to an engine fails as `ENGINE_UNSUPPORTED_OPERATION` and creates nothing; `sessions.discardDraft` is never routed. Creation targets an engine via explicit `engine` (`'pi'` forces Pi, unknown ids fail as `INVALID_ARGUMENT` even with zero engines) or via an owned `model.providerId`, stamping `session.engine` on the detail. An engine without a `sessions.create` handler cannot be a create target: an explicit id fails as `ENGINE_UNSUPPORTED_OPERATION` while provider routing skips it and falls back to Pi. Prompt-family commands run through the same send-dedup boundary, so operation ids, receipts, `STALE_STREAM_EPOCH`, and `OPERATION_PAYLOAD_MISMATCH` behave identically and `sessions.sendReceipt` works unchanged; a result without a `messageId` fails as `MALFORMED_DAEMON_RESPONSE`. `engines.list` returns `{ engines: [{ id, label, commands }] }` (`{ engines: [] }` with zero engines) and `runtime.health` advertises `engines.list`; `GET /api/pi/engines` projects the same shape through a whitelisting projector and maps daemon errors without returning an empty list. Listings append engine rows (tagged `session.engine`, directory forced) after Pi rows and engine providers after Pi providers, skipping id collisions (a collision marks that engine failed); `incompleteEngines` names failed engines and appears only when non-empty. Failure is never empty success: a throwing, timed-out (10s default), or malformed engine listing drops all that engine's rows, and the current browser catalog does not yet act on `incompleteEngines`, so a UI that renders engine sessions must treat such a listing as non-authoritative for those engines before relying on destructive cleanup. Each listing call receives an AbortSignal aborted when its per-engine timeout fires, and concurrent `listSessions` calls for one directory (plus concurrent `listProviders` calls) share one in-flight result that clears on settle; failures are never cached. All engine output (event payloads, detail/command results, list and provider rows, snapshot fields) is redacted in core with `redactAttachmentValues`, so an echoed server-local attachment path never reaches the wire; the registry and router refuse to build without a redactor. Snapshots for engine sessions come from sync `engine.snapshot()` framed with daemon-owned sequence/`lastSequence`/epoch/`sessionId`/`directory` using the snapshot's own absolute directory; a throw logs and writes nothing, and a non-object/undefined/missing-directory result returns nothing, like an unavailable Pi session. Registry creation awaits factories in order (a throwing factory is logged and skipped; a duplicate/invalid id/label/shape disposes already-created engines and throws `INVALID_ENGINE`), ownership-check throws count as not owned, and `stop()` disposes every engine (AggregateError on failure, mirroring the runtime registry) without blocking remaining teardown. Logging records only engine id, short event name, and stable error code, never messages, payloads, credentials, or paths. Extension, resource, settings, and provider-auth commands stay Pi-only. Pending-input contract: engines MAY carry `inputState: { pending }` on list rows, snapshot fields, and detail results, where `pending` is `{ count, kind, since }` (`count` an integer 1..99, `kind` `'input'` or `'approval'` with `'approval'` marking a permission-style request, `since` epoch ms of the oldest open request) or `null` when authoritatively nothing is pending; a missing or malformed value falls back to the daemon index without failing the row. Engines MUST publish `session.input { pending }` on every pending-input transition for live updates: the daemon normalizes the summary, folds it into the pending-input index (hosted requests win when both exist), republishes it canonically as `{ pending, serverNow }`, rejects a malformed summary as `INVALID_ARGUMENT`, and rejects a summary for a session the publishing engine does not own as `INVALID_ARGUMENT` without applying it (a throwing ownership check counts as not owned); an engine `session.deleted` also clears that engine's index state. Engine notifications are live-only: engines publish `extension.notify { message, level }` through the host wrapper; the daemon normalizes the level (`'info'` unless `'warning'`/`'error'`), caps the message at 2000 characters, and publishes through the usual redaction. An empty message is a silent no-op. Nothing is stored, so engine snapshots and details carry no notice history. `session-engine-router.js` owns the dispatch, create targeting, merges, snapshot payloads, publish wrapper, and `engines.list` description behind dependency injection; `session-daemon.js` keeps one-guard call sites.

## Sandbox launchers

A sandboxed project runs its sessions in a separate daemon started through a launcher (#242). `../sandbox/` owns everything else about it, documented in `../sandbox/DOCUMENTATION.md`: the launcher seam, the nono launcher and profile, the per-project setting, the manager, its routes, switching, staleness, OAuth, and trust reset. This section covers the daemon side. Only Pi session daemons (the agent) run in the sandbox. PiChamber's own Git panel, terminal, browser and GitHub features, and worktree hooks and start commands, run outside it with the user's access, so git config, hooks or filters an agent writes into the repo can run when the user or the Git panel runs git. This is a known, accepted trade-off. With no sandboxed project, `createPiSessionDaemonSupervisor` without `launch` spawns exactly the command it always did.

- Identity and profile key. `identity` hashes the launcher id, its probed version, the hash of its policy file, the grants, and the network. The sandbox daemon's profile key is `<server profile key>-sbx-<project key>-<identity>`, where the project key is a hash of the project root. A change to any input starts a new daemon; the same inputs reuse the running one through the normal reuse path. The daemon's own profile folder (read-write) and runtime folder (socket bind) derive from that key, so the supervisor adds them to the grants after hashing. The runtime folder is named `sbx-<first 16 hex of sha256(profile key)>` rather than the full key, so the socket path fits macOS's shorter address limit.
- Liveness and stop. The sandbox can write the daemon's profile folder, so its state sidecar and `runtime.health` answer can be forged. The supervisor never signals a pid from them, and reads the sidecar only as a small regular file (no symlink, no FIFO). The credential it sends on every request is kept in the launcher folder, which the sandbox can read one file of and write nothing in; the daemon's environment carries none of the server's own `PICHAMBER_*` variables but the data and agent folders. Known limit: after a server crash, a sandbox daemon whose grants then change (a worktree added, a host changed) has a different profile key, so the next server never finds its record and it keeps running with its old grants until it exits; a graceful shutdown stops every daemon. After spawning a launcher daemon, it records the launcher's `child.pid` with an identity (Linux: start time from `/proc/<pid>/stat`, zombies count as gone; macOS: `ps` state and start time, one-second resolution; elsewhere none, so no record) and the owning `serverInstanceId` in `<dataDir>/pi/launchers/<profileKey>/launcher.json`. The operation lock for a launcher daemon is `operation.lock` in that folder. No sandbox grant covers it, and the daemon never touches the lock. If the record cannot be written, the launcher gets SIGTERM and the start fails with `DAEMON_LAUNCHER_RECORD_FAILED`. A claim on reuse rewrites the record's owner. Stop with a record: the record's owner must be this server instance (otherwise `DAEMON_OWNERSHIP_MISMATCH`). The supervisor then asks for `runtime.shutdown` where the sidecar allows it; a missing, forged or refused answer does not block the stop. It sends SIGTERM to the recorded pid only while its identity still matches, waits for that process to exit (`DAEMON_STOP_TIMEOUT` otherwise), and removes the record. A pid now held by another process is not signaled. Stop without a record (a daemon started before records existed) signals nothing and only waits for the sidecar pid to exit. Under `nono run` (0.82.0), the launcher is nono's supervisor process. It forwards SIGTERM to the daemon and exits after it. The daemon stays in nono's process group, because it has no terminal and nono makes no new session for it. The group is not signaled: the daemon would get SIGTERM twice, and its one-shot handler would let the second kill it mid-shutdown. On Linux nono's network-mediated path also sets `PR_SET_PDEATHSIG` (SIGKILL) on the daemon; its plain fork path does not, so a SIGKILL to nono there would orphan the daemon. Sidecar pids are still read for liveness only, where a lie hurts nothing but that sandbox's own availability: refusing a start (`DAEMON_UNAVAILABLE`), the stale-endpoint check (which unlinks only the socket inside its own runtime folder), stale-sidecar removal in its own profile folder, and the `runtime.health` identity match. A start also refuses while a recorded launcher is still running. The start-timeout signal goes to the `child.pid` just spawned. Test: `supervisor-launcher-stop.test.js`.
- Fail closed. `createSandboxedPiSessionDaemonSupervisor` probes first. When the launcher cannot sandbox, it throws `SANDBOX_UNAVAILABLE` with the probe's `reason` and spawns nothing. It also refuses `SANDBOX_ENDPOINT_TOO_LONG` when the sandbox socket path would not fit a Unix socket address (107 usable bytes on Linux, 103 on macOS), because the daemon's listen would fail with `EINVAL` and exit without a state sidecar. A grant or network that fails validation, or a launcher `prepare` error, surfaces as that error's code and spawns nothing. The shared `PICHAMBER_PI_SESSION_DAEMON_ENDPOINT` override never applies to a sandbox daemon.
- Tests. `../sandbox/nono-launcher.test.js` maps a fake nono's answers to each probe code. `supervisor-sandbox.test.js` injects `spawn` and asserts the exact nono command, flags, environment, profile file, shadow links, profile-key reuse and change, refusals, and fail-closed probe. `supervisor-sandbox-nono.e2e.test.js` runs a real turn whose bash tool checks what it can touch under real nono; it skips itself when the nono probe fails (Linux CI and the development container have no Landlock), so run it on a Landlock machine before a release. `.github/workflows/sandbox-macos.yml` runs it on macOS with `PICHAMBER_REQUIRE_NONO_E2E=1`, which turns the skip into a failure.
- Session leases across the boundary. A lease file name hashes the agent folder, the cwd, and the session id. A sandbox daemon's `--agent-dir` is the shadow, so the supervisor also passes `--lease-agent-dir <real agent folder>` (`prepareProjectSandbox` returns it as `leaseAgentDir`) and `createSessionDaemon({ leaseAgentDir })` keys leases on it. The main daemon and a sandbox daemon then compute the same lease file and exclude each other on one session.
- Events. A sandbox daemon joins the merged `/api/pi/events` stream when it starts (the manager re-registers it, so the pool's `onChange` subscribes it) and leaves when it stops idle or is turned off; its frames carry its `stream` id. A session read routed by its transcript is stamped with the stream of the daemon that served it, not the request's (absent) directory.
- Sandboxed folders (`createSessionDaemon({ isSandboxedDirectory })`, default: none). `daemon-process.js` sets it from `--sandboxed-folders-file`, which the supervisor passes only to a daemon started without a launcher (the main daemon). Every runtime creation (`startRuntime`, `sessions.open` of a persisted session, `sessions.create`) refuses such a folder with `DIRECTORY_SANDBOXED`. `defaultDirectory()` replaces the active folder with one outside every sandbox while the active folder is sandboxed, and catalog reads that name a sandboxed folder use the same folder (`outsideSandbox`). See `../sandbox/DOCUMENTATION.md`. Test: `session-daemon.test.js` ("never starts a runtime in a folder a sandbox daemon owns").
- Read-only reads (`sessions.readPersisted`). Given `sessionId` and an optional `directory`, `before`, and `limit`, the daemon finds the session's JSONL like `sessions.open` does and parses it with Pi's `parseSessionEntries` into `SessionManager.inMemory` (no persistence). It then projects messages and pages exactly like `sessions.open` / `sessions.messages`. It starts no Pi runtime, extension, or tool, takes no lease, and writes nothing, including no trust decision for the folder it reads from. Pi's file loader can append a newline to repair a file; this path does not use it. The result is `readOnly: true`, idle, `isStreaming: false`, and `lastSequence: -1`, with no `streamEpoch`, `inputState`, extension state, or bash executions. The sandbox manager uses it on the main daemon while a project's sandbox cannot start. Test: `session-daemon-read-persisted.test.js`.

## Deliberate limits

This module defines the authenticated session API boundary consumed by the Pi-native session UI. Session leases coordinate PiChamber daemons only: the standalone `pi` CLI runs its own foreground runtime and does not honor these leases, so concurrently editing the same session through PiChamber and `pi` remains unsupported until Pi provides compatible upstream locking. Resource configuration and richer attachment extraction remain owned by their dedicated workstreams. The session event stream is SSE over the existing authenticated runtime transport; WebSocket callers fall back to it, preserving direct and relay behavior without a second daemon listener. The public route emits named heartbeat events so native `EventSource` clients can detect a silent foreground connection, reconnect, and resume from their last accepted sequence.

The Pi SDK is pinned exactly at `1.5.0`. Any Pi upgrade requires a deliberate SDK/release-note review and repeat of this module's disposable-runtime smoke validation.

## SDK upgrade validation

The 1.4.0 to 1.5.0 upgrade needs one daemon change, keybinding hints for extension renderers, and no PiChamber data migration. The SDK removes and renames no public export. It adds the `KeybindingHints` and `PackageInstallFailure` types. The session JSONL format is unchanged. What changed in the SDK and how it affects PiChamber:

- Keybinding hints. `ToolRenderContext`, `MessageRenderOptions`, and `EntryRenderOptions` now extend `KeybindingHints`. The daemon builds the first two itself, so without this change an extension that called `ctx.keyHint()` threw and lost its custom render. `extension-keybindings.js` now supplies both functions without terminal keys, because PiChamber does not bind Pi's shortcuts. The daemon runs no entry renderers, so `EntryRenderOptions` needs nothing. An extension that imports `keyText` or `keyHint` from the package instead reads Pi's process-wide keybindings, which nothing sets in an SDK host, so `app.*` ids render without keys and `keyHint()` keeps a leading space.
- Tool argument validation. Validation runs on `@earendil-works/pi-schema`. TypeBox features outside JSON Schema (`Type.Refine()`, `Type.BigInt()`, codecs) no longer apply, plain JSON Schema tools such as MCP tools get the same coercion as TypeBox tools, and the model sees pi-schema's error text (`- path: missing`). PiChamber registers no tools and asserts no validation text. The extension loader still maps `typebox` and `@earendil-works/pi-ai` imports, and the manual fixture `../fixtures/pichamber-gui-demo.ts` uses only `Type.Object` and `Type.String`.
- Model catalog. The bundled catalog moves to models.dev v2. OpenCode drops `deepseek-v4-flash` for `deepseek-v4.1-flash` and sends each model to a protocol-specific endpoint such as `https://opencode.ai/inference/openai/v1`. Realtime and image-only models are no longer chat models, and the default OpenAI model is `gpt-6.1-sol`. PiChamber hardcodes no model ID. A session or `settings.json` that selects a removed model still opens, falls back like any missing model, and keeps its settings file unchanged (`sdk-upgrade.test.js`). A provider-level `baseUrl` in `models.json` still applies to every OpenCode model, so it also replaces the new per-protocol endpoints.
- MCP OAuth. `oauth.clientRegistration` defaults to `"auto"`, which signs in with Pi's Client ID Metadata Document when the authorization server supports it and registers a client otherwise. Clients registered earlier stay in use while their redirect URI matches. PiChamber binds extension UI in `tui` mode, so `/mcp login <server>` signs in inside Pi's MCP manager surface: the authorization URL as a link, and an input for pasting the redirect URL when the browser cannot reach the daemon host's callback. Nothing is opened on the daemon host (`builtin-extensions.js` passes a no-op `openUrl`). `session-daemon-mcp.e2e.test.js` opens and closes the manager but has no OAuth server, so sign-in itself is untested.
- `pi.exec()`. It gains `maxBuffer` and a `truncated` result, kills a command with SIGKILL 5 seconds after an ignored SIGTERM, and stops splitting UTF-8 characters. Pi runs it and the daemon does not wrap it. PiChamber's `!cmd` path uses `AgentSession.executeBash`.
- Extension update changelogs. Only Pi's interactive mode reads and records `extensionChangelogVersions`. The daemon does neither, so the next `pi` CLI launch still shows the notice.
- Project trust. A saved "do not trust" decision now wins for a project without trust-requiring resources, for example one with only `AGENTS.md`. Runtimes resolve trust through Pi. The daemon's settings view already reported such a project as denied, and now the runtime agrees.
- Session writes. A failed append now removes the entry from memory, so later entries no longer point to a missing parent. The daemon's rename path opens a new `SessionManager` per call and needs no change.
- Built-in extensions. The installed CLI lists the same built-ins as 1.4.0.
- Dependencies. The pi-* packages move to 1.5.0 and add `@earendil-works/pi-schema`. `minimatch` moves to 11.0.3 and `undici` to 8.12.3. pi-ai and pi-agent-core drop their direct `typebox` dependency, and pi-coding-agent keeps `typebox` 1.3.27.

The 1.0.0 to 1.4.0 upgrade needs no daemon code change and no PiChamber data migration. What changed in the SDK and how it affects PiChamber:

- OpenCode endpoints. Bundled OpenCode Zen and OpenCode Go models moved from `https://opencode.ai/zen/v1` to `https://opencode.ai/inference/v1` (1.3.0). A provider-level `baseUrl` in a user's `models.json` still overrides every model of that provider, cached remote models included, so a saved `zen/v1` override keeps sending requests to the old endpoint. `sdk-upgrade.test.js` derives the override from the bundled model instead of hardcoding a URL.
- Azure rename. The `azure-openai-responses` provider is now `azure` (1.0.3). Users rename the key in `auth.json`, `models.json`, and `settings.json` or log in again. PiChamber does not reference the provider ID.
- Extension run start. `before_agent_start` is a union on `messageType` and also fires for `pi.sendMessage(..., { triggerTurn: true })` runs, and the session counts as busy while a run starts (1.2.0). Extensions need the change. The daemon's own prompts are unaffected: preflight, steer, and follow-up still pass `session-daemon-turn.e2e.test.js`.
- Theme schema. Theme files load with `https://pi.dev/schemas/theme.schema.json` validation at startup (1.2.0). PiChamber's extension theme is built in memory and does not load theme files.
- `kimi-coding` uses Chat Completions, and a `models.json` base URL override must include `/v1` (1.3.0). This is user configuration with no PiChamber change.
- Built-in extensions. The installed CLI lists no built-in that `builtin-extensions.js` neither loads nor skips.

The 0.85.1 to 1.0.0 upgrade keeps the public session runtime/services API and the v3 JSONL format. No PiChamber data migration or cache deletion is required. Existing settings, custom model definitions, labels, and extension entries remain intact.

What changed in the SDK and how PiChamber handles it:

- Prompt acceptance. `preflightResult` now receives a disposition (`'started'`, `'queued'`, or `'handled'`) and is not called for a rejected prompt. The daemon treats any callback as acceptance and a rejected prompt promise as rejection. Under 0.85.1 the callback received a boolean, so the old `=== true` check rejected every prompt on 1.0.0.
- Session file timing. The SDK writes the JSONL when the first user message is appended. 0.85.1 waited for the first assistant message. A turn that fails or is aborted after its user message now leaves a persisted session. An untouched session, and a first prompt rejected before the user message, still persist nothing.
- New entry types. `context_edit` and `usage` entries are not transcript rows. History projection reads only `message` entries with the `user` or `assistant` role and the custom entries described above.
- Nested tool calls. Calls made through `ctx.executeTool()` emit `tool_execution_*` events with `parentToolCallId`. The daemon does not publish them, which matches history.
- Model catalog. Remote catalog requests carry `types=chat,image,classifier`. PiChamber lists models through `getModels()` and `getAvailableSnapshot()`, which stay chat-only.
- Theme. The extension theme adds `appearance`, `colors`, and `style()`.
- Built-in extensions. The Pi CLI's list of built-ins is not a public export. `sdk-upgrade.test.js` reads it from the installed package and fails when Pi ships a built-in that `builtin-extensions.js` neither loads nor lists as skipped, so a new upstream built-in needs a decision at upgrade time. It also checks that each loaded entry keeps the CLI's `builtin` and `replaceable` flags.

- `sdk-upgrade.test.js` exercises the installed SDK with disposable directories: cached OpenCode models with provider query parameters (`?types=chat%2Cimage%2Cclassifier`), user model additions and overrides, forced HTTP refresh, ETag/304, failed refresh preserving the last catalog, restart restoration, and opening/appending a session with context edit or usage entries.
- `session-daemon-extensions.e2e.test.js` exercises real extension loading, commands, dialogs, GUI projection, reload, and session disposal.
- `session-daemon-turn.e2e.test.js` runs real agent turns through the installed SDK with an offline provider registered by an extension: prompt acceptance, streamed text, an extension tool with custom renderers whose result calls `ctx.keyHint()`, a nested `ctx.executeTool()` call, the session file after the first turn, steer and follow-up queued while streaming, a first prompt rejected with no usable model, and a stored session that holds `context_edit` and `usage` entries.
- `session-daemon-plugins.e2e.test.js` loads the bundled Visuals plugin through `plugins.configure` in a real runtime: no `render_html` before configuration, recreation on enable, a real `render_html` call whose `details` arrive as tool `metadata`, and a state-only change that removes the tool declaration (Pi appends a `toolsRemoved` system message) without recreation.
- `session-daemon-mcp.e2e.test.js` runs real turns against a stdio MCP server the test writes to disk: a `direct` tool row with its rendered call and result, `/mcp` opening Pi's MCP manager as a capturing `custom()` surface whose frame lists the fixture server, then closing it, a `codemode` script whose row shows the nested call in progress and then the script output with no separate nested row, `tool_search` loading a `deferred` tool that is then called, `-builtin:mcp` disabling the extension and its command, an installed extension that registers `/mcp` replacing the built-in, a server whose command does not exist leaving a normal prompt unaffected, and the server process exiting when the daemon stops.
- `supervisor.test.js` covers authenticated replacement of a daemon from an older PiChamber build. Normal versioned releases must retain that replacement behavior. Same-version, same-path manual dependency replacement is not a release upgrade and requires stopping the old server/daemon before restarting.
- The SDK CLI bin moved to `dist/bundle/cli.js`; the detached daemon already resolves `package.json`'s `bin.pi` rather than hardcoding the old location.
- `pi-runtime-smoke.test.js` checks the pinned SDK and foreground backend in real subprocesses with disposable dirs. It checks the SDK import with pinned version parity, bundled `bin.pi --help`, credential-free `rpc get_state` to success, and a credential-free foreground `serve --foreground --api-only` that polls `/api/pi/runtime` to ready and checks parent and daemon `execPath`. It is not provider E2E. It defaults to `process.execPath` and accepts an absolute override in `PICHAMBER_TEST_RUNTIME`. See `packages/web/bin/lib/DOCUMENTATION.md` for runtime rules and CI matrix.

The bundled OpenCode catalog removes `deepseek-v4-flash-free`. SDK remote catalogs still merge additively with bundled models, so this upgrade fixes that stale entry, not general upstream deletion propagation. Explicit user-defined models with the same ID remain supported. Do not clear users' `models.json` or `models-store.json` to apply an upgrade.
