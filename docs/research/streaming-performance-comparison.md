## Bottom line

* **No repo is a drop-in performance reference for PiChamber.** Each targets a different runtime boundary, so the mechanism that actually determines perceived streaming cost is not portable without adopting its boundary.
  * MonoCode is Tauri (Rust child-process harness → Tauri IPC → React). Its streaming path never leaves the local machine (`src/lib/harness/child.ts` `harness_spawn`/`harness_write`/`harness-stdout` events) and therefore has no WebSocket/SSE compatibility constraint.
  * T3 Code is a server-centric Effect monorepo (server owns provider sessions, WebSocket `WsRpcGroup` fan-out to web/desktop/mobile via `apps/server/src/ws.ts`). Its live path is global-event-store + per-thread subscriptions.
  * Waku is a Rust/GPUI native desktop (`crates/waku-daemon` + `crates/waku-protocol` + `waku-client`) with a `waku:`-borne browser client (`apps/web`, `packages/waku-client`). Its transcript is a GPUI `list` with a Rust markdown pipeline, not a web virtualizer.

* **Reusable mechanisms that survive the runtime difference:** RAF-batched transcript state commits (MonoCode), sequence-gated incremental live overlays that keep settled history at frozen identities (PiChamber), heavy work on the correct side of the boundary (highlight as pure paint), pagination over bounded snapshots instead of unbounded replay on reconnect, and a single shared animation clock.

* **Invalid direct comparisons:** Tauri IPC vs browser SSE, local SQLite persistence vs a server event store, GPUI native lists vs web virtualizers, and bundled Rust binaries vs Electron packages. These differ at the product requirement level, not only the implementation level.

* **PiChamber's current documented strengths that none of the three invalidate:** one Pi SSE stream per runtime with LRU-capped transcripts (`reducer.bySession`, idle-eviction cap 16, `scripts/perf` validity guarantees), RAF cadence-batched live-tail overlay with frozen identities and settle-time highlighting, explicit failure vs empty-success discrimination, and a Capacitor surface that splits `CapacitorHttp` vs direct `EventSource` for SSE. Those invariants have no measurement-backed replacement in the inspected repos.

## PiChamber current documented architecture (baseline)

Derived only from the five listed PiChamber docs (no speculation from Pi daemon source beyond what the docs project).

### Live streaming

* **Transport:** Single SSE stream `GET /api/pi/events` with comment heartbeats. WebSocket branch exists in the UI transport (`packages/ui/src/lib/pi/transport.ts` per `docs/research/external-tunnel-support.md`) but the Pi-native server exposes no Pi event WebSocket route — SSE-only is authoritative. `runtimeFetch`/`RuntimeAPIs` boundary per `packages/web/README` surface docs.
* **Event cadence / batching:** Ordered per-directory flush as one reducer batch (`sync/DOCUMENTATION.md`: "event pipeline delivers each ordered per-directory flush as one reducer batch"). Within that, **streaming assistant text is cadence-batched once per animation frame before reaching the markdown renderer**. `buildLiveStreamingEntry` patches only the streaming assistant; unchanged sibling messages keep identities so `ChatMessage` memo can skip. Only token or tool updates on the live tail re-project.
* **State subscription granularity:** `PiSessionStore` owns one cluster per runtime (`reducer.bySession`, `hydratedSessionIds`, `lastAccessById`, `catalog` metadata-only `byId`/`byDirectory`/`listStatusByDirectory`). Providers write into that one map; UI hooks (`useSessions()`, `useSessionMessageRecords()`, `useSessionParts()`) subscribe to narrow slices. `useSessionMessageRecords` freezes live-tail text by default (reads `selectStreamingAssistantMessageId` / `streamingMessages`) and reuses the previously published records array — ChatContainer, composer, status row share the hook so a token does not re-project the whole transcript in each. `useUserMessageHistory` treats assistant-part mutations as equal. `useSessionParts` remaps live parts by reducer-part identity. `useSessionReducerPart` hydrates one part on `session:{id}` only while expanded.
* **Content identity:** `contentIndex` identifies a content block, not an individual delta; repeated deltas for the same index append in sequence order, with sequence rejection owning replay protection. `lastSequence` cursor guards `getSession` restores.

### Reconnect / resume

* **Cursor:** `lastSequence` per session drives both live and hydrated paths. Reconnect merges snapshot into existing cluster without disposals, then hydrates any resident session whose `lastSequence` is behind the resumed cursor. `getSession` includes live assistant/tools while the daemon streams; later `session.snapshot` force-hydrates to avoid a missed replay window freezing the chat. Live or sequence-newer content overlays a fetch; a fetched settled cursor that is at least as new replaces stale overlapping content.
* **Recovery bounds:** Incomplete-session materialization deduped by runtime/directory/session for the full cooldown window; `session.idle`/`session.error` with a pending/running trailing tool triggers a narrow tail refresh, not a full refetch.

### Transcript rendering for large histories

* **Windowing:** Large history is virtualized — `profile:session` validity checks verify that "a virtualized large history can replace rows without increasing the number of mounted message elements." Pagination on demand; placement via `SessionMessageLoader` (runtime+directory+session authority, one in-flight request shared/promotable, generation-checked commits).
* **Markdown / highlighting during streaming:** Live tail overlays parts onto the streaming message only. **While streaming, Shiki and KaTeX stay off for every block**; the unstable live tail is a growing text node in a full-width paragraph (`breaks: false`) rather than marked/morphdom HTML. Unfinished fences/lists/quotes keep `pre-wrap`. Highlighting and math land on the settle pass. Renderer freezes settled leading markdown blocks and re-lexes only the source tail; while the live tail is the last block, append-only token updates **write that text node directly and skip the async block/HTML pipeline**. Live thinking is a max-height plain-text pane that auto-collapses when that thinking part settles.
* **LRU / collapsed hydration:** Transcripts LRU-capped (soft cap 16, idle-eviction via deferred microtask, never evicts selected/busy/retry/pending-prompt, retains `lastSequence`). Collapsed settled Task cards contribute no child-session hydration; historical Task detail hydrates on expand.

### Mobile responsiveness

* **Shell:** Capacitor for native iOS/Android (`packages/mobile/README.md`); bundles `mobile.html→index.html`, always `MobileApp`. Reuses the web build, connects to an existing PiChamber server. Connection screen + `Instances` are Capacitor-only; LAN needs UI password + `0.0.0.0` bind + firewall rule.
* **Layout:** Single navigation model on phones and tablets: left sessions drawer (~72% phone, dark scrim), right workspace drawer (~80% from right), shared slide motion and sidebar surface; tablet is a **live size class (`useTabletLayout`, short side ≥600px)**, not a device check (foldables adapt). Terminal PTY and dictation run on the server over the shared authenticated runtime transport; microphone audio streams as binary PCM.
* **Mobile transport:** `CapacitorHttp` for ordinary API requests, **but direct-LAN `EventSource` transport for `/api/pi/events`** — intentional because `CapacitorHttp` buffers long-lived SSE. Native resume replaces the `EventSource` and continues from its last accepted sequence; WKWebView may preserve a dead connection without reporting an error. Diagnostics: bounded redacted client log via `Export diagnostics`.

### Animation choices

* `scripts/perf/DOCUMENTATION.md` `profile:animation` fixture enforces the rule **animate `transform` and `opacity` only**. Measured costs (fixture, 1–32 elements): `transform`/`opacity`/`filter` → 0 style recalcs/layouts per second; `rotate` (individual property), `background-position`, `border-color`, `box-shadow` → 60 recalcs/s; `width` → 60 recalcs + 60 layouts/s. In-app Performance HUD (`packages/ui/src/lib/perf/DOCUMENTATION.md`) is a 4 Hz DOM text overlay with a single `rAF` sampler, disabled by default (`localStorage.pichamber_perf_hud`), and must stay off during CDP captures.

### Desktop packaging / binary size

* `packages/electron/README.md`: `main.mjs` starts `@pi-chamber/web/server/index.js` **in-process** (no sidecar, no external binary). Dev: HMR; packaged: staged assets via `pichamber-ui://` while loopback server remains the authenticated API backend. Windows specifics: sessions under `%USERPROFILE%\.pi\agent`, private IPC named pipe, bash via Git for Windows. Brand assets generated via `bun run icons:brand`; macOS `Assets.car` via `generate:macos-icon` on Xcode. Releases via `.github/workflows/release.yml`, desktop default artifact.

## MonoCode (`hardbeat920/monocode@ab435a0`)

**What it is:** Tauri desktop (React 19 + Vite + Tailwind 4) multiplexing local CLIs for Claude Code, Codex, Cursor, Grok Build, OpenCode, Pi, omp, fx. Provider names in `src/lib/session.ts` `HarnessId`. README: "Tabs are sessions. The composer is the input. MonoCode does not sell tokens." Build: `npm run tauri dev` (`src-tauri/src/main.rs`).

MonoCode's equivalent of sequence-rejection is `joinStreamText` snapshot detection.

### Reconnect / resume

| Dimension | Primary source | Behavior |
|---|---|---|
| **Cursor** | `src/lib/harness/piFamily.ts:Resume {sessionId,cwd}`, `stateFor(flavor).resumeByThread: Map<string,Resume>` + `liveByThread: Map<string,Live>`; `src/lib/inFlight.ts:canAutoContinue`, `wasTurnInterrupted`, `INTERRUPT_MESSAGE` | No server sequence. ### Animation choices

## T3 Code (`pingdotgg/t3code@9b2d043`)

**What it is:** Effect-based monorepo (`vp`/`vite-plus`, `Effect`, `@effect/atom`, `pnpm@11.10`). One `t3` server (`apps/server`, Node 24) drives provider CLIs (`apps/server/src/provider/Layers/*Adapter.ts`: `ClaudeAdapter`, `CodexAdapter`, `CursorAdapter`, `GrokAdapter`, `OpenCodeAdapter`) and exposes an `effect/unstable/rpc` + `WsRpcGroup` surface (`packages/contracts`, `packages/client-runtime`, `apps/server/src/ws.ts`). ### Reconnect / resume

| Dimension | Primary source | Behavior |
|---|---|---|
| **Cursor / snapshot** | `apps/server/src/ws.ts:SHELLSUBSCRIBEShell` (`SHELL_RESUME_MAX_GAP 1000`, `THREAD_RESUME_MAX_GAP 1000`, `loadSnapshot` vs `readEvents(afterSequence, replayGap)`), `packages/contracts/src/orchestration.ts:OrchestrationSubscribeShellInput {afterSequence, requestCompletionMarker}`, `OrchestrationSubscribeThreadInput {afterSequence, requestCompletionMarker, turnLimit, beforeCursor}`, `apps/server/src/orchestration/Services/ProjectionSnapshotQuery.ts` + `apps/server/src/orchestration/Layers/ProjectionSnapshotQuery.ts:getThreadDetailSnapshot`, `apps/web/src/historyBootstrap.ts`, `apps/web/src/state/threads.ts` | **Sequence-gated, bounded replay, then snapshot fallback.** Both `subscribeShell` and `subscribeThread` attach the live `streamDomainEvents` queue *before* reading snapshot/replay state so no post-subscribe event is lost. If `afterSequence` is supplied: compute `replayGap = headSequence - afterSequence` from `latestSequence`; if `0 ≤ gap ≤ 1000`, replay exactly `[afterSequence, headSequence]` (capped, not chasing a moving head) and `Stream.concat(catchUp, bufferedLive)`. Otherwise (gap<0 cursor ahead, or >1000 far behind, commented as "OOM-killed servers on large databases"): **fall back to a fresh snapshot** (`OrchestrationShellSnapshot` / `OrchestrationThreadDetailSnapshot`) concatenated with the same buffered live tail. A `requestCompletionMarker:true` inserts a `{kind:"synchronized"}` marker between catch-up or snapshot state and live events. ## Cross-cutting: reusable mechanisms vs invalid product comparisons

### Mechanisms worth carrying across runtimes

These show up in at least two of the three repos or directly address a PiChamber `sync/DOCUMENTATION.md` / `scripts/perf` invariant without requiring a runtime swap.

* **One frame, one commit for the streaming tail.**
  MonoCode's `scheduleHarnessFlush` (RAF, or 32ms in background; approval events bypass) is the clearest small reference. PiChamber already batches text deltas `once per animation frame` and overlays only the live tail, leaving sibling records at frozen identities so `ChatMessage` memo skips. T3 Code's Effect `Stream`/`Queue` boundary sits server-side; Waku's GPUI `cx.notify()` coalesces at the display link. MonoCode's batteried RAF pattern is the cleanest to lift into a web store's hot path.

* **Tail is append-mostly; settled history is frozen.**
  PiChamber's settled-block freeze + direct text-node write for the live tail has the same shape as Waku's `volatile_from` cache (re-flatten one block, reuse settled flats; veil opacity animates paint only) and T3 Code's `LegendList` stable rows + coarse pagination windows. The lesson is not virtualizer choice but "never re-parse settled markdown to emit one more token."

* **Highlighting is paint, never layout.**
  Waku states it explicitly ("Color is paint, geometry is layout") and uses a line lexer → `TextRun` colors so highlighting can arrive without reflowing. PiChamber's "Shiki/KaTeX off while streaming, highlight on settle" is the web equivalent. T3 Code's `ChatMarkdown` with live Shiki is the counter-example — it works because the diff surface virtualizes separately, but it loses the "stream never reflows" invariant.

* **Bounded replay, snapshot fallback, watermark split, live-buffer-first ordering.**
  T3 Code's `THREAD_RESUME_MAX_GAP/SHELL_RESUME_MAX_GAP = 1000`, `readEvents(afterSequence, replayGap)` vs fresh `Snapshot`, global `snapshotSequence` + per-page `threadSequence`, and `Queue.unbounded<…LiveBuffer>` fork-before-read are general. PiChamber's `lastSequence` + per-directory generation guard + `synchronized` tail cover the same concerns at a smaller scope. MonoCode's per-provider `providerSessionId` resume and Waku's `provider_cursor` watermark are different cursor kinds that convey the same "cursor is per-owner, not per-tab" rule.

* **One shared animation clock, parked when idle.**
  Waku's `PulseClock` (33ms tick, 300ms leases, strided `spin_slow` for expensive subtrees) maps directly onto web: one `requestAnimationFrame` loop, notify only leased views, park when idle, reduced-motion → phase 0. MonoCode's individual `requestAnimationFrame` per spinner and T3 Code's multiple `view-transition` animations are the cases to avoid.

### Product / runtime differences that make a direct "faster" claim invalid

* **Transport mismatch.** PiChamber uses SSE for `GET /api/pi/events`, T3 Code and Waku use WebSocket, and MonoCode uses local IPC. Replacing one with another changes the server, mobile, authentication, and relay contracts. It is an architecture decision, not a local performance fix.

* **Who owns the session file.** MonoCode persists `blocks_json` into a local `rusqlite` WAL DB; Waku persists via `waku-daemon`'s task SQLite + `~/.waku/projects`; T3 Code persists in the server's `OrchestrationEngine` event store; PiChamber persists via the Pi daemon's session JSONL and the `PiSessionStore` LRU. "No virtualization needed because SQLite is small" or "SQLite is faster than SSE" are format comparisons, not rendering comparisons.

* **Virtualizer engine.** PiChamber's virtualized history, T3 Code's `LegendList`, Waku's GPUI `list`, and MonoCode's 20-turn slice are four different schedulers with four different overscan/measure caches. Without the same workload (same 200-turn tool-heavy history, same `initialTurns` cap) rendered under `bun run profile:session`'s output-normalised metrics, adding a virtualizer is ceremony, not evidence.

* **Desktop artifacts.** MonoCode uses Tauri, Waku uses Rust and GPUI, and PiChamber and T3 Code use Electron. PiChamber and T3 Code also ship a Node server. Compare measured release artifacts and their included capabilities, not framework names.

* **Mobile stack.** PiChamber's Capacitor+`EventSource` SSE split vs T3 Code's Expo+WebSocket native app vs no mobile (MonoCode, Waku). The mobile "streaming perf" question for PiChamber is the WKWebView dead-connection resume + `CapacitorHttp` buffering trap documented in `packages/mobile/README.md`, not a web re-layout.

## What maps directly onto PiChamber today

* **Keep the streaming contract conservative.** The inspected repos reinforce PiChamber's `scripts/perf/DOCUMENTATION.md` stance: production-build CDP traces are the source of truth; `transform`/`opacity` only; compare per-character-output-normalised metrics via `session-summary.json` / `idle-summary.json` under `--baseline` + `--budget-*`. MonoCode's shimmer (`background-position`) and T3 Code's `width/height` tooltip transitions are exactly the properties the fixture flags — do not add them to streaming hot paths.

* **Borrow T3 Code's resume constants and barriers.** Pin a documented gap constant (T3 Code's `1000`) and the `synchronized` barrier onto PiChamber's `lastSequence` case analysis, even though PiChamber's cursors are per-session not global. The "subscribe live queue before reading replay/snapshot" ordering already mirrors T3 Code's `Queue.unbounded` fork — keep it explicit in `sync/DOCUMENTATION.md`.

* **Steal Waku's MarkdownView shape for the web tail.** The web equivalent of `volatile_from` + `RowVeil` is exactly PiChamber's settled-block freeze + trailing text-node direct write. The gap to close is the Shiki/KaTeX deferral invariant stated but not yet enforced by the web virtualizer's measure pass — Waku's "one shaped element per block, one `shape_text` call, GPUI cache reuses verbatim" comment is the spec for where to put the web equivalent if a regression appears.

* **Park the perf HUD.** Waku's `PulseClock` parking when no leases remain is already what `packages/ui/src/lib/perf/DOCUMENTATION.md` describes as "a boolean check on counter hot paths and no overlay, rAF, or observers" while disabled. Apply the same parking to any future web pulse (don't leave a per-message spinner's `requestAnimationFrame` alive outside the streaming window).

* **Do not chase desktop or mobile shape changes for perf.** Swapping Electron ↔ Tauri ↔ GPUI or Capacitor ↔ Expo is a product roadmap decision (PiChamber's in-process server vs T3 Code's sidecar `t3` server vs Waku's split daemon is the real tradeoff). The performance handoff from this note is the narrow, runtime-agnostic list above.

## Caveats and remaining work

* No throughput, frame-rate, heap, or binary-size measurements were produced here — by design per instructions and because PiChamber's `scripts/perf` harnesses require a production-build server + reproducible dense workload. Any future "we improved streaming by X%" must be a `bun run profile:session|idle --baseline … --budget-*` comparison on the same thread fixture (PiChamber's `scripts/perf/DOCUMENTATION.md` "Never report an after without a before" rule) plus a before/after browser trace.
* Harness cost scales with history depth and tool density (open `buildActivityPhases`, number of `TranscriptBlock`s, provider JSON size). MonoCode's comment "Tokens arrive many times per frame" suggests frame cost depends on coalescence, not just token count — instrument via `localStorage.pichamber_session_load_perf=1` + HUD before concluding a bug is absent.
* Mobile and desktop packaging claims remain at the dependency+config level. Checked `package.json` / `Cargo.toml` / `tauri.conf.json` / `electron-builder` configs but did not build installers or run simulators, so binary sizes and cold-start times are intentionally absent.
